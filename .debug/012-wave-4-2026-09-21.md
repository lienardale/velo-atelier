# 012 — W4 integration: hardening a tree that four branches had each hardened alone

**Date** 2026-09-21 → 22 · **Status** resolved · **Wave** W4 (T1 coverage, security
and integration completion · T2 performance · T3 visual regression and the e2e
matrix · T4 docs)

W4 adds no product surface. It proves §7.6 on a PR to `main`: every gate is
exercised, and the ones only a merged tree can hold are measured on it. The
arrangement is W3's: four worktrees, each with its own `_test` database and
port, and an implementer followed by an adversarial reviewer per task. Two
things were added, both because of `.debug/010`:

- a lock that runs heavy commands one at a time;
- the artefacts that depend on all four branches (visual and perf baselines,
  Lighthouse pins, the lazy-chunk pin, the payload ratchet) are produced from
  the merged tree, by CI where CI is the only honest source.

Each task wrote its own note: `.debug/013` (T1), `.debug/014` (T2),
`.debug/015` (T3). This one has the rulings, what the integration found, the
gates, and the deviations.

## 3. Process: three usage limits, a lock, and a reboot

**Usage limits** interrupted the work three times: during the four
implementations, during the T1–T3 reviews, and during the integration review.
Every agent committed as it went, so each resumption was a continuation brief
(its commits, where it stopped, what remained, its predecessor's transcript)
rather than a restart. Nothing was lost except wall-clock time.

**The lock.** In the first run, four agents plus an amd64 container drove this
8-core Mac to a load average of 45, and T2's pre-push was refused twice on 5 s
unit-test timeouts. Those are `.debug/009`'s timeouts, and they measured the
machine, not the code. From then on, builds, `ci.sh`, pushes, Playwright, the
container and Lighthouse ran one at a time behind an `flock(2)` held by a perl
wrapper. The kernel releases the lock when its holder exits, so a dying agent
cannot leave a stale one. Load held at 6–8, and reached 19 only during one
local 8-URL × 3 Lighthouse run. The three reviews took about three hours, most
of it spent waiting for the lock. That was worth it: no timing in this wave was
taken under contention, and no test failed for load.

**The Mac rebooted** during integration, after the local gates and
measurements and before the push. The reboot cleared `/private/tmp`, which held the orchestrator's
scratchpad: the briefs, the lock wrapper and the integration notes. It also left
Docker Desktop down, which is a stop-and-ask. Everything that mattered had
already been committed, or was in the session transcript. The one lesson:
nothing that has to survive the session goes in `/tmp`.

## 5. The integration review

Three lenses read the merged diff for things no single branch could show:
**security** of the new surfaces, **docs-truth** (claims against the code) and
**gates-and-contracts** (gates that exist only on the merged tree, and contracts
that moved under a sibling). The last two were cut off by a usage limit and
re-run.

**Security**, three P2s:

- **A write token next to branch code.** `perf.yml`'s `update-snapshots` held
  `contents: write` and `pull-requests: write` while it ran the dispatched
  branch: `npm ci` with every install script, `next start`, the Playwright
  global setup (migrate + seed), and the specs. Both write-token jobs also left
  the token in `.git/config`. The rule "a write-token job builds and tests
  nothing" was already written, but had been applied only to the perf-baseline
  job. The snapshot job is now split in two:
  - `record-snapshots` runs with the read-only token and uploads the PNGs;
  - `update-snapshots` checks out without persisting the token, downloads the
    images, refuses anything that is not a PNG, and opens the PR.

  `(verify)`: create-pull-request v7 (`22a9089`) saves and unsets any persisted
  credential, installs its own, and restores the original afterwards
  (`src/git-config-helper.ts`), so `persist-credentials: false` costs it
  nothing. (`3cee01e`)

- **The CSRF table walked the wrong set.** It read only files named
  `actions.ts`, and only `export const … = withUser(`. `googleSignInAction`,
  which writes `NEXT_LOCALE` before it leaves for Google, was in no table. The
  walk now reads every `"use server"` module under `app/`, whatever the file is
  called. It splits the `withUser` exports from the others, and fails on an
  export it cannot name or on an inline `"use server"`. The four anonymous
  actions form one table: a cross-origin POST and a POST with no Origin are both
  `FORBIDDEN`, with nothing reached. (`3cee01e`)
- **Quotas are counted, then written**, with nothing held in between. Parallel
  requests from the owner can therefore overshoot a quota by as many requests as
  they keep in flight, and only inside their own account. This is post-MVP, with
  the fix written down: a per-bike `pg_advisory_xact_lock` inside the transaction
  (`docs/backlog.md`).

**One mutation check was not run, and the replacement is better.** The plan was
to delete `guardSameOrigin()` from `googleSignInAction` for a moment and watch
the new test fail. The session's auto-mode classifier blocked that as a
security-weakening edit, which is reasonable: the edit is indistinguishable
from the attack the test is for. The proof took a form that needs no such edit.
Each anonymous action now has a permanent **control**: a same-origin request
whose side effect the probe must see (Auth.js's `signIn` called, the
`NEXT_LOCALE` cookie set, a `User` row written). The probe therefore cannot be
vacuous, and the `FORBIDDEN` assertion covers the rest. The walk's three failure
modes were planted in scratch copies of `app/`, never in the tree:

- an unlisted export in a file not named `actions.ts`;
- an inline `"use server"`;
- a re-export.

Each one failed with a message naming it.

**Docs-truth and gates-and-contracts**, plus a second security pass, re-run after
the usage limit. That made 17 findings, some of them the same one seen from two
sides. Each was checked against the lines it cited before anything changed.
Every one held.

- **P0 (gates): the merged tree had no visual baselines.** T3's 20 PNGs existed
  only on its dry-run bot PR (#2). They were recorded on `w4/t3` before T1, T2
  and T4 were merged, and never merged themselves. Playwright 1.63's default
  `updateSnapshots: "missing"` writes a missing baseline and **fails** the test,
  without a retry. Both required legs, `e2e (desktop-chromium)` with 7 tests and
  `e2e (mobile-chromium)` with 13, would therefore go red on the first CI run of
  the merged tree. The macOS matrix, which skips `visual.spec.ts` off Linux,
  cannot show it. The probe run then confirmed it exactly: those 20 tests
  failed, and nothing else (run 35658114694). The fix is the one dispatch on the
  final tree (§11), not a cherry-pick of the stale set.
- **P1 (gates): the soft tier compared nothing.** There was no
  `tests/perf/baselines/` on the tree, so `compare.ts` only warned "no baseline"
  and §7.3's >300 % failure did not exist. The one recorded set (PR #3)
  predates both the five-tap median and `--workers=1`. The same dispatch fixes
  it.
- **P1 (docs):** the index lacked 013–015, and four places cited this note
  before it existed. The W5 launch checklist said Alltricks and Decathlon were
  unverified, the opposite of `retailers.ts` since the retailer pass. My own
  draft of §4 claimed the build list appears in the screenshots; it does not.
- **P2 (gates):** a dispatched `perf.yml` reported a check named `build`, which
  is a REQUIRED context, on the PR's head commit, so whichever `build` finished
  last decided it. The job is now `build (nightly)`, and `required-checks.test.ts`
  refuses a required name in any other workflow.
- **P2 (gates):** a PR touching only workflow files skipped every job but lint,
  including the unit tier that holds the CI and guard contract tests.
  `.github/workflows/**` now counts as code.
- **P2 (gates):** the perf runner label spelled the Playwright version in a form
  Renovate's lockstep rule does not match, so compare.ts's runner-mismatch
  warning could never fire. It is now spelled as the image reference.
- **P2 (docs):** every doc prescribed a bare `npm run build` for e2e and
  Lighthouse. That bakes `.env.local`'s `:3000` origin into the canonicals that
  `seo.spec.ts` and Lighthouse's SEO category check on `:3100`, the trap
  `.debug/010 §8` recorded. They now say `bash scripts/ci/build.sh`.
- **P2 (docs):** the lazy-chunk pin also lowered `lighthouserc.cjs`'s derived
  bike script ceiling, from 625 664 to 612 272 B, and `perf.budgets.json` did
  not list that reader. The merged tree's bike pages transfer 566 379 B, which
  is 7.5 % under it.
- **P2 (docs), stale text:**
  - the CSRF contract in `CLAUDE.md`;
  - the serial-workers "open lever" in the perf doc;
  - two comments naming `update-snapshots` as the job that records;
  - the build list's measurement drawings, missing from the barrel's importers;
  - the nightly's duration.
- **P2 (security): raw NUL bytes.** Five tracked files each held one raw NUL
  inside a string literal. One of them is `lib/auth/safe-callback-url.ts`, the
  open-redirect guard. A NUL makes git and GitHub show a file as binary: W4's
  own 30-line edit to `tests/security/path-traversal.test.ts` appeared in its
  review as `Bin 6297 -> 7776 bytes`. Each is now the escape sequence for
  U+0000, which is the same string at run time.
  `tests/unit/source-files-are-text.test.ts` now fails on any C0 control
  character in a source file. Its first run caught one: its own doc comment,
  where the agent's file-writing tool had decoded the escape it was given into
  the raw character. That is very probably how the other five got there.

## 6. Two flakes, both fixed at their cause

**The sheet.** The host matrix ran 1 985 tests and failed one: mobile-chromium, "the sheet
reports where it is and moves when the handle is dragged (fr)", on
`not.toHaveAttribute("data-snap", "2")` after the second drag. Twelve repeats
at a load of 7–11 gave one failure. The test waited a fixed
`waitForTimeout(400)` before reading the handle's box. The sheet animates for
`--sheet-duration`, so under load the second drag started from mid-animation
and landed somewhere else. The wait now polls `getAnimations()` until nothing is
running. After the fix it passed 32 of 32 repeats across the mobile projects
(`bb4bc12`). No timeout grew: the test now waits for the event itself instead of
guessing its length.

**The part panel.** The probe run's desktop leg reported one flaky test (it
passed on retry): "a saved bike's edit goes through the server action (fr)".
It clicked the cassette row straight after `goto`, then waited 45 s for an
attribute select that never came. A saved or demo bike's rows are
server-rendered, so they are on screen before React listens, and a click in
that window is dropped. This is `.debug/011`'s lesson for the decision tree, on
another page. Every row click in `part-panel.spec.ts` now goes through
`clickRow()`, which waits until React owns the node, the check `visual.spec.ts`
already uses. The bike3d specs wait for the viewer to be ready first, so they
were never exposed.

## 12. The first real comparison, and the ruling it needed

PR #6 was the first run compared against real baselines. Its CI went red on
`perf`, and on one metric only: `perf-mobile` / `mtb-full-dropper-1x12`
counted **6 long frames against a baseline of 1**. That is 350 % on the
smoothed ratio, past the 300 % line. The code was byte-identical to the
nightly that had recorded the baseline an hour earlier.

A long frame is an rAF interval over 50 ms during three one-second orbits:
§7.3's hitch, as a visitor on a GPU would see one. Under SwiftShader it is
mostly the rasteriser's own scheduling. The nightly's own five repetitions,
identical code on one runner, show the spread:

| perf-mobile preset      | long frames per repetition | median |
| ----------------------- | -------------------------- | ------ |
| `mtb-full-dropper-1x12` | 4, 1, 1, 1, 3              | 1      |
| `city-igh-8-hub-motor`  | 3, 0, 0, 3, 1              | 1      |
| `road-rim-2x11`         | 0, 4, 6, 4, 6              | 4      |
| `mtb-hardtail-1x12`     | 0, 5, 2, 3, 1              | 2      |

The first repetition is not consistently the worst, so this is not a cold
start. The runner makes it worse. PR #6's runner was about 10 % slower (p50
frame cost 105–114 % of baseline on every preset). A re-run of the same job
landed on one about 40 % slower (136–147 %), and there long frames reached
5–18 against baselines of 1–7, with six failures and up to 750 %. On that same
slow runner the durations stayed well clear of the fail line:

| Metric      | vs baseline, slow runner |
| ----------- | ------------------------ |
| p50 frame   | 136–147 %                |
| p95 frame   | 135–151 %                |
| build       | 96–118 %                 |
| tap latency | 88–136 %                 |

So the fail line on long frames measured the runner, and a required check built
on it would have gone red on PRs that changed nothing. **Ruling (the user,
2026-09-22): long frames only warn on a software renderer.**

`scripts/perf/ladder.ts` now holds the ladder as pure functions:

- `verdictOf()` caps `longFrames` at a warning when the run's `renderer` names
  a software rasteriser;
- `SOFTWARE_RENDERER` is the list the local GPU gate refuses, now shared by
  `tests/perf/bike3d.perf.spec.ts`;
- `compare.ts` marks such a row "warn (software renderer)".

`tests/unit/perf/ladder.test.ts` pins the PR #6 case both ways (warn in
software, FAIL on a GPU). It also checks that the durations keep their failure
in software, and that the ladder is still `perf.budgets.json`'s 150 / 300.
Each direction was mutation-checked: without the cap, and with the cap
widened to every metric, the matching test fails. Run end to end on synthetic
run files, `compare.ts` exits 0 with the capped warning on the CI renderer and
1 on the M2's.
