## 2. Two tests timed out at 5 s — on the runner, not here

```
FAIL  unit  lib/bike3d/scene.test.ts > planScene > draws conditional parts iff the spec needs them
FAIL  unit  tests/unit/content/check.test.ts > known-bad fixtures > the CLI prints file:line: message …
Error: Test timed out in 5000ms.
```

Both had been passing. Nothing in the five commits since the green run touched
either file: they were already close to the limit and something — a slightly
larger module graph to instrument, a slower runner — pushed them over.

**The machine ratio, measured rather than guessed.** Four unchanged tests of the
same file, CI against this Mac running `vitest --coverage` exactly as CI does:

| test                                      | CI      | local (coverage) | ratio |
| ----------------------------------------- | ------- | ---------------- | ----- |
| `brands.yaml: missing, invalid, …`        | 3652 ms | 1359 ms          | 2.69× |
| `every rendered part is checked …`        | 1915 ms | 638 ms           | 3.00× |
| `a tool label missing from a catalogue …` | 2011 ms | 688 ms           | 2.92× |
| `steps and consequences`                  | 2192 ms | 707 ms           | 3.10× |

**≈ 2.9×.** That number is how the fixes below were sized: a test is safe when
`local-with-coverage × 2.9` leaves real headroom under 5 s. Note the second
multiplier hiding in here — v8 coverage roughly triples these tests on this
machine too, so a timing measured with a plain `vitest run` is off by ~8× from
CI and will mislead you.

### The fix is the one `solver.test.ts` already made: do less, not wait longer

A per-test timeout is a hang detector, and this repository has raised one before
with a reason (`}, 20_000); // real zxcvbn, same lazy dictionary load`). It was
not the right tool here, because in both cases the time was going somewhere
avoidable.

**`lib/bike3d/scene.test.ts` — 61 200 assertions in a loop.** The test ran
`enumerateBuilds()` _inside_ the test body (6 800 builds, ~250 ms) and then made
nine `expect().toBe()` calls per build. `expect` is not free: each call builds
chai matcher state and, under v8 coverage, is instrumented. The enumeration
moved to module scope — import time is not charged to a test's timeout, which is
exactly what `solver.test.ts:24` does and for the same reason — and the nine
invariants became a `CONDITIONAL_PARTS` table compared in plain JS, collecting
mismatches into a `Set` and asserting **once**.

Same strength, better failure: the old loop stopped at the first bad build; the
new one reports every distinct spec shape that is wrong. Mutation-verified —
flipping `"internal-gear-hub"` to `!== "igh"` fails the test with the offending
specs named; restoring it passes.

**`tests/unit/content/check.test.ts` — four full parses of 47 guides.** The CLI
test ran `runCli` four times and `buildContentManifest(REPO)` once, each a
complete parse of the corpus. Three changes, none of which drops an assertion:

- `--strict` and `--emit` ride in **one** run. `code === 0` from that run proves
  the ★ rules pass; the stdout it prints proves `--emit` wrote.
- `buildContentManifest(REPO)` moved to a module constant (`REPO_MANIFEST`) —
  two tests wanted it, and it is read-only.
- the "no `--emit` → nothing written" run now uses an **empty** root. It asserts
  a property of the CLI, not of the emitted tree, and the default-root (cwd)
  path it exists to cover is unaffected.

The eight fixture tests also each copied the corpus and parsed it a second time
to ask the same question — "is this message absent from a clean corpus?". That
is now one copy and one parse per mode (`cleanRoot()` / `cleanErrors(strict)`).

### Result

| test                          | CI before | local+cov before | local+cov after | CI projected |
| ----------------------------- | --------- | ---------------- | --------------- | ------------ |
| `draws conditional parts …`   | 5271 ms   | ~1400 ms         | 643 ms          | **~1.9 s**   |
| `the CLI prints file:line: …` | 5114 ms   | ~1600 ms         | 769 ms          | **~2.2 s**   |

The whole file dropped from 17.6 s to 14.9 s locally under coverage; on CI it
was the single slowest file in the tier at 48 s.

## 3. `npm run ci:local` had never once proved the test hooks stay out

Found because `build` failed locally _after_ the two test fixes, with the exact
symptom `.debug/004 §1` was written about:

```
✗ no test hooks — 1 hit(s)
  .next/static/chunks/3-clkjdzr5pm_.js
```

Not a regression, and not a stale artifact — the chunk was written by that
build. `.env.example` ships `NEXT_PUBLIC_TEST_HOOKS=1` (line 37, since the
scaffold commit — a developer wants `window.__va` in `npm run dev`), every
developer's `.env.local` is a copy of it, and **`next build` loads
`.env.local`**. So the flag was on for every local build.

That inverts the guard. `scripts/bundle-guard.ts` asserts the marker is present
**iff** the flag is set, so with the flag on locally it was asserting the
_present_ direction — the same direction CI's `build` job asserts, because that
job sets `NEXT_PUBLIC_TEST_HOOKS: "1"` for the artifact the e2e matrix consumes.

**Nothing in the repository ever asserted the absent direction.** `.debug/004 §1`
says "CI exercises the present direction; `npm run ci:local` and Vercel exercise
the absent one", and `scripts/ci/build.sh`'s own header says the same. Both were
true only of the hand-run build the author used to verify the fix, with the
variable unset in the shell. Vercel _is_ genuinely covered — no `.env.local` in
the deploy, no such variable in the project env, and `scripts/vercel-build.sh`
runs the guard — so production was never at risk. The claim about `ci:local` was
wrong from the day it was written.

**Fix** — `scripts/ci/build.sh` pins the flag off unless the caller set one:

```bash
export NEXT_PUBLIC_TEST_HOOKS="${NEXT_PUBLIC_TEST_HOOKS:-0}"
```

A real environment variable beats every `.env*` file, so this wins over
`.env.local` and loses to CI's `env:` block — which is precisely the split the
header describes. Verified: the guard now reports `no test hooks — 0 hit(s)`
across 50 files on a local `ci:local` build, and CI's build job still finds the
marker.

`.env.example` is deliberately left alone: `1` is the right default for
`npm run dev`, and the gate is now enforced where builds are gated rather than
by asking every developer to remember.

**Lesson (a second helping of `.debug/004`'s).** "This command exercises that
direction" is a claim about a command, and a command's environment is not the
environment you verified in. The way to check a two-sided guard is to run the
command that is supposed to enforce it and watch it fail.

## 4. §1.3 / §5.2 review of the dev-CSP change (`03317b2`)

Reviewed rather than rewritten — it was already on `main` when this session
started, not uncommitted as expected.

- **Production is byte-identical to plan §1.3.** `contentSecurityPolicy()`
  builds `script-src 'self' 'unsafe-inline'` and appends `'unsafe-eval'` only
  when `NODE_ENV !== "production"`; no nonce, so no route is forced dynamic
  (§1.3), and `tests/security/csp-header.test.ts` pins the production string
  character for character and asserts the two variants differ in that one token.
- **The switch fails open**, and deliberately: an unrecognised `NODE_ENV` gets
  `'unsafe-eval'` rather than silently serving a dev build a policy it cannot
  satisfy. The comparison is exact, and the test feeds it `"Production"` and
  `"prod"` to prove neither turns the relaxation off.
- **§5.2's real guarantee is upstream of the header** — MDX is compiled at build
  time, so nothing evaluates in the browser. Asserted on the build output by
  `scripts/bundle-guard.ts` (`no runtime evaluator — 0 hit(s)`, 50 files).
- **Gap, assigned:** §5.2 wants `tests/e2e/csp.spec.ts` asserting that exact
  production header on `/fr` and `/fr/velo/demo`. It does not exist yet —
  `tests/e2e/guides.spec.ts` covers one route today. The spec is **W3-T4's**
  (plan §8.4), and its task block requires both routes.
