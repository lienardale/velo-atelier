# 016 — W5: the first deploy, and four gates that had never met reality

**Date** 2026-09-29 · **Status** resolved · **Wave** W5 (launch)

All four findings are of the same shape: a file or a step written in an earlier
wave, correct on its face, that nothing had ever executed. One is read only by
Vercel, one only by branch protection, one only by a preview deployment, one
only by Renovate — and none of them existed until the day W5 turned them on.

The common lesson is not about any one of them. A configuration file whose only
reader is a third-party service gets its first test in production, however many
green gates the repository has. Three of the four were caught by the service
saying so; the third was caught by asking the database a question instead of
asking the health endpoint.

---

## 1. `.vercelignore` dropped `tests/`, and `next build` type-checks them

The first production deployment (`velo-atelier-hf4s0ou97`, `main` @ `76e6032`)
failed after two minutes with more than 200 TypeScript errors:

```
components/ui-ext/SkipLink.test.tsx(4,32): error TS2307: Cannot find module '@/tests/_helpers/intl'
components/ui-ext/Stepper.test.tsx(10,17): error TS2339: Property 'toHaveAttribute' does not exist
lib/checkup/build-list.test.ts(6,52): error TS2307: Cannot find module '@/tests/_helpers/checkup'
playwright.config.ts(40,33): error TS2307: Cannot find module './tests/e2e/_fixtures'
Failed to type check.
```

`.vercelignore` (W4) kept `.debug/`, `.claude/`, `docs/` **and `tests/`** off the
build machine. But `next build` type-checks the whole tsconfig project, and this
repository keeps unit tests **beside the code** (`components/**/*.test.tsx`,
`lib/**/*.test.ts`). Those files import `@/tests/_helpers/*` and
`@/tests/_fakes/*`, and the jest-dom matcher types come from `tests/` too. Remove
the directory and the sources that remain no longer type-check.

**Why nothing caught it.** `.vercelignore` is read by exactly one thing: a Vercel
build. CI builds the whole checkout, `npm run build` locally builds the whole
checkout, and no test asserts on the ignore file. The first execution of that
file was the first production deploy.

**Fix.** `tests/` ships. Only what the type-checker never reads stays out:
`tests/e2e/__screenshots__/` and `tests/perf/baselines/`.

**How to detect a regression.** A preview deployment on any branch: it applies
the same `.vercelignore`. The preview for PR #8 built clean and logged
`▶ skipping prisma migrate deploy (VERCEL_ENV=preview)`, which is what
`docs/deploy.md` §2 asks a preview to print.

## 2. Path filters and required contexts cannot both be right

Branch protection went on first (W5, §4.1): 20 required contexts, read from
`REQUIRED_CHECKS`. The fix above was a two-file PR — `.vercelignore` and a doc —
so `ci.yml`'s `dorny/paths-filter` job decided the change touched no `code`
path, and 14 of the 20 jobs skipped. The PR was `BLOCKED`, and not only because
a skipped job fails to satisfy a required context:

**A skipped matrix job reports the template, not its expansions.** The `e2e` job
is named `e2e (${{ matrix.project }})`. Skipped, it reports one check run with
that literal name; the five required `e2e (desktop-chromium)` …
`e2e (no-webgl)` contexts never report at all and sit at "Expected — waiting for
status to be reported" for ever.

`tests/unit/ci/required-checks.test.ts` already carried the rule, in the reason
it gives for keeping `visual-baseline-guard` non-blocking: "a required context
that never reports blocks the merge forever". The filters inside `ci.yml`
contradicted it for every PR that touches only docs or deployment config.

**Fix.** Every `ci.yml` job runs on every pull request. The `changes` job and its
filters are gone, `coverage` keeps `!cancelled()` so a red test tier still turns
it red rather than skipping it (§7.6 AC12), and `detect changes` left
`NON_BLOCKING_CONTEXTS`.

The cost is real: a docs-only PR now runs e2e, Lighthouse and perf. The
alternative is a single aggregate context that always runs and summarises the
others — a change to `REQUIRED_CHECKS`, branch protection and §7.6 AC12, worth
doing only if the runner time starts to hurt.

**How to detect a regression.** Open a PR that touches only a `.md` file: all 20
contexts must report.

## 3. The `preview` Neon branch had no schema, and every check said it was fine

`docs/deploy.md` §1.3 creates a Neon branch `preview` from the default branch,
shared by every preview deployment. W5 created it on 2026-09-23, the day the
Neon project was made — six days before the first production deploy.

`scripts/vercel-build.sh` runs `prisma migrate deploy` **only** when
`VERCEL_ENV=production`. That is deliberate (§2: a preview must not migrate),
and it means nothing else ever will. So `preview` was branched from an empty
`production`, production was migrated later and alone, and the preview branch
stayed at zero tables indefinitely.

**Why every check passed anyway.** The two things W5 actually probed on a
preview deployment cannot see a missing schema:

- `GET /api/health` is a bare `SELECT 1`. An empty database answers it, so the
  preview returned `{"ok":true,"db":true}` — which §2's check treats as proof
  the database is good.
- `/velo/demo` is code-backed (`lib/bike/repo.ts`: demo is read-only and never
  a row), so it returns 200 against any database, or none.

A preview's first real query would have thrown `relation "User" does not
exist`, at sign-in — the one flow `docs/deploy.md` §3 says previews are tested
with, because Google cannot complete on a preview URL.

**How it was actually found.** Not through HTTP. The two Neon endpoints were
queried directly for `count(*) from "_prisma_migrations"`:

```
ep-quiet-river-…  migrations=2  last=2026-09-29T08:11:43Z  tables=12   # production
ep-plain-block-…  ERROR relation "_prisma_migrations" does not exist   # preview
```

The same two lines after `prisma migrate deploy` against the preview branch's
**direct** URL:

```
ep-quiet-river-…  migrations=2  last=2026-09-29T08:11:43Z  tables=12
ep-plain-block-…  migrations=2  last=2026-09-29T09:19:06Z  tables=12
```

**Fix.** Migrate `preview` by hand, once, and again after any migration
production takes; or reset the branch from its parent in the Neon console.
`docs/deploy.md` §1 now carries both, with the assertion to run first — the
direct URL of the _preview_ endpoint, checked by host before anything runs,
because the neighbouring string in the same file is production's.
Superseded on 2026-10-06 by [`.debug/017`](./017-w5-closeout-2026-10-06.md) §4: `.github/workflows/migrate-preview.yml` is what migrates `preview` from now on — once bootstrapped: it had never run that day, nor on 2026-10-07, and its first dispatch, pending on the maintainer, is also the bootstrap — the one by-hand form left runs `scripts/ci/migrate-preview.sh`, and a reset from the parent is no longer advised — per Neon's documentation it copies production's data and schema into `preview`.

**How to detect a regression.** `select count(*) from "_prisma_migrations"` on
both branches must return the same number. `/api/health` will never tell you.

## 4. `renovate.json` was invalid, and stopped Renovate dead

Installing the Renovate app (§4.4) produced no dependency dashboard and no
PRs — only issue #9, "Action Required: Fix Renovate Configuration":

```
Configuration option `vulnerabilityAlerts.minimumReleaseAge` should be a string,
Invalid configuration option: _comment_minimumReleaseAge
```

Renovate stops **all** PRs on a config error, by design, so the symptom is
silence rather than a bad update.

Both mistakes date from W1 and had never run. `renovate.json` is read by
Renovate and by nothing else: no ESLint rule, no `tsc`, no CI job and no
JSON-schema check in this repository ever parsed it, and the `$schema` line at
the top is honoured by editors, not by any gate. Its first reader was the app.

Renovate's own schema (`renovate-schema.json`) settles both:

- `minimumReleaseAge` is `{"type": ["string", "null"], "default": null}`.
  `false` is not a member of that type; `null` is how an inherited hold is
  released, which is what `vulnerabilityAlerts` wanted — a security fix must
  not wait out the 7-day supply-chain hold.
- `description` is a first-class option at every config level (string, or array
  of strings). The rationale had been parked in an invented `_comment_*` key,
  which Renovate rejects like any other unknown option. The prose moved into
  `description` unchanged in substance.

The old comment also claimed the 7-day hold was "required by the semgrep rule
renovate-missing-minimum-release-age". No such rule runs here:
`scripts/ci/sast.sh` loads `p/owasp-top-ten`, `p/typescript`, `p/javascript`,
`p/nextjs` and `p/react`, none of which reads `renovate.json`. The hold is kept
because it is right, not because a gate demands it, and the new `description`
says that instead.

**How to detect a regression.** `renovate-config-validator` is shipped inside
the `renovate` package and reads the file directly:

```bash
npx --yes --package renovate -- renovate-config-validator renovate.json
```

Run on `main`'s version of the file it exits **1** and prints, word for word,
what issue #9 said:

```
ERROR: Found errors in configuration
       "file": "renovate-old.json",
       "errors": [
         {
           "topic": "Configuration Error",
           "message": "Configuration option `vulnerabilityAlerts.minimumReleaseAge` should be a string"
         },
         {
           "topic": "Configuration Error",
           "message": "Invalid configuration option: _comment_minimumReleaseAge"
         }
       ]
```

On the fixed file it exits **0** with `INFO: Config validated successfully
against 1 file(s)`. So the whole of this finding was reproducible locally, in
one command, on the day the file was written — nobody ran it because nothing
asked them to. Worth a CI job the next time this file is touched: it is the
only reader of `renovate.json` the repository can host itself. The install is
slow (the validator pulls the whole `renovate` package, minutes on a cold
cache), which is the argument for a path-filtered job — and, per §2 above, for
keeping such a job OUT of the required contexts.
Superseded on 2026-10-06 by [`.debug/017`](./017-w5-closeout-2026-10-06.md) §4.7: the command above is unpinned and, handed a filename, validates it as a global config; the check is now `bash scripts/ci/renovate-config.sh` (`renovate@44.108.1`, `--no-global`), run by `.github/workflows/renovate-config.yml`, whose first run on a GitHub runner passed in 41 s.
