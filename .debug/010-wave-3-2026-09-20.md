# 010 — W3 integration: what four parallel branches could not see

**Date** 2026-09-20 · **Status** resolved · **Wave** W3 (T1 checkup, T2 build
list + shop, T3 guest import, T4 SEO/legal/edge states)

Four tasks, four git worktrees, four Postgres databases on one container, four
Playwright ports. Every task reported its acceptance commands green, and every
task was then reviewed by a second agent that re-ran them, read the branch diff
against the plan, and repaired what it found before the branch was merged.

This note is about the two things that arrangement cannot catch: a contract that
moves under a sibling, and a gate that only exists on the merged tree.

---

## 1. The reviews paid for themselves before integration

Four branches, four adversarial passes, 39 findings. The four that mattered:

| Task | Finding                                                                                                                                                                                                           | Why no gate caught it                                                                                                                |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| T1   | For a SAVED bike the stored checkup was never restored: the page read it through `loadCheckupAction`, and `withUser` → `guardSameOrigin` refuses a request with no `Origin` header — which is every document GET. | The repo's own `tests/security/csrf-and-actions.test.ts` pins that refusal. Nothing asserted the resumed page, so it 404'd silently. |
| T1   | `deriveBuildList` applied `markRechecked` to lines it had just derived, so an OK on any OTHER question sharing an `(action, partId)` closed a line a KO had just opened — 22 such pairs in one demo checkup.      | `(action, partId)` is the identity of a LINE, not of a question. The unit tests used a three-step fixture where no pair collided.    |
| T4   | Three of `JsonLd.test.tsx`'s nine assertions could not fail: react-dom 19.2.8 rewrites `<script` / `</s` itself, so the breakout cases stayed green with `serializeJsonLd` reduced to plain `JSON.stringify`.     | Mutation testing. Nothing else finds a test that passes both ways.                                                                   |
| T4   | `expect(body).toContain("Disallow: /fr/velo/")` is also satisfied by `Disallow: /fr/velo/[id]` — a rule matching literal brackets, leaving every real bike crawlable.                                             | A substring assertion over a generated file. Mutation-verified by removing the `[`-truncation.                                       |

The lesson is the one `.debug/004 §1` already states, applied to tests rather
than to gates: **an assertion that cannot fail is not an assertion.** Both T4
findings came from deliberately breaking the source and watching the test stay
green. That is now the house move for anything load-bearing.

## 2. A contract moved under a sibling, and the fixture is what said so

W3-T1 grew `CheckStepRef` by three required fields (`title`, `prompt`, `number`)
and `CheckupState` by a required `symptoms`, after W3-T3 had written its guest
fixture against the version committed to `main` before the branches were cut.

`lib/guest/schema.test.ts` stopped compiling. That is the design working:
W3-T3's report says it built the fixture "as a typed `CheckupState` so the file
stops compiling if the type moves". A fixture typed as `unknown` would have
compiled and tested a shape that no longer exists.

The importer itself was never at risk, and the reason is worth keeping:
`StoredCheckupSchema` is `z.object`, not `strictObject`. A guard over data
**this application wrote in an earlier version of itself** must drop what it
does not recognise; a guard over data **a visitor supplied** must refuse it.
`lib/guest/schema.ts` has both, a few lines apart, and gets the direction right
in each: `GuestStateSchema` is `strictObject` throughout.

The fixture now builds its steps with W3-T1's own `makeStep`, so the next field
the planner adds costs nothing here.

## 3. Four things needed the other branch to exist

Each was correctly identified and deliberately left by the task that found it —
which is what made them cheap at integration rather than expensive.

**The retailer host allow-list (§4.4).** W3-T3 validated `chosenProduct.url` as
plain https and said so, because the retailer data was on a sibling branch.
`retailerHosts()` now derives the host set from `RETAILERS` itself, so a new
retailer or a changed template moves the guard with it, and a product claiming
`vendor: "alltricks"` while pointing at `evil.example` — or at the suffix
`www.alltricks.fr.evil.example` — is refused. Mutation-verified.

**The stored build-list envelope.** W3-T3 accepted two plausible shapes because
nothing committed said what `va:buildlist:<ref>` holds. It turned out not to be
W3-T2's at all: `writeGuestBuildList` (W3-T1) is the only writer. The reader
narrowed to `{version, updatedAt, items}`, and its test now goes through that
producer instead of a hand-built literal.

**`markRechecked` had no production caller on either path.** §5.4's "a later OK
on a part with an open item marks it done" and §6.7's row for it existed as a
pure function, a unit test and an e2e row, and were wired to nothing. The guest
path additionally OVERWROTE the stored list on every finish, discarding the
`done`, `refinement` and `chosenProduct` the visitor had typed. Now
`mergeGuestBuildList` merges on `(action, partId)` — the key the server already
merges on, deliberately not the item id, which embeds a step key that moves
between runs — and `finishCheckupAction` closes matching open lines on the
bike's other lists.

The e2e row that was supposed to prove this read `va:checkup:local`, where the
list lives under `va:buildlist:local`. It could never have passed. It was in
W3-T4's deferred set and had therefore never run — **a deferred test is an
unrun test, and an unrun test is not evidence of anything.**

**A mock that named one collection.** W3-T4 added the `legalPage` collection and
fixed its own mock; `lib/content/collection.ts` reads both collections at module
scope, so two of W3-T1's files failed on import with "No `allLegalPages` export
is defined on the mock".

## 4. The privacy policy's tables rendered as pipe characters

W3-T4 called this a genuine plan contradiction and refused to invent a third
option, which was right: §1.4 pins the dependency set, `remark-gfm` is not in
it, `content/legal/confidentialite.{fr,en}.mdx` (W2-T4b) is GFM, and adding a
dependency on one of four parallel branches collides in `package-lock.json`.
Confirmed on the served page: zero `<table>` elements, and the
data / purpose / legal-basis rows as paragraphs of pipes.

Resolved at integration, where the lockfile has one writer: `remark-gfm@^4`, for
the **legal collection only**. GFM also turns on strikethrough, autolinks, task
lists and footnotes, and how the 47 guides parse is a content decision for a
wave that owns the guides. `npm audit` gains nothing.

The table also needed a scroll container of its own. Three columns of prose do
not fit 320 px, and §6.8 AC5 measures `document.documentElement.scrollWidth` on
every mobile project — a bare wide table would have failed every mobile page
visit after it. `tests/e2e/seo.spec.ts` now asserts the rendered `table` role,
that the page contains no `| ---`, and that the wrapper is what scrolls.

## 5. The timeout `.debug/009` predicted, three days later

`.debug/009 §2` named `tests/unit/i18n/client-namespaces.test.ts` as the next
test to cross the 5 s budget, measured its worst case at 3.8 s, and said the
honest fix would be a shared graph walk rather than a bigger number.

W3 added six routes to the walk. Two cases crossed: `app/[locale]/page.tsx` at
5320 ms and `guides/[slug]/page.tsx` at 5061 ms under coverage.

The test resolves each route's client subtree independently, and the graphs
overlap almost completely — `lib/i18n/navigation`, the domain barrel and the UI
primitives are in all of them. Source text was already cached; the parsing was
not, so `ts.createSourceFile` re-parsed every shared module once per route.
Three caches keyed by path, each a pure function of the file's bytes (text,
import specifiers, `"use client"`-ness, and the `useTranslations` scan):

|                            | before   | after      |
| -------------------------- | -------- | ---------- |
| whole file, under coverage | 30.3 s   | **2.9 s**  |
| slowest case               | 5 320 ms | **320 ms** |

At the ≈2.9× CI ratio measured in `.debug/009`, that is ~0.9 s against a 5 s
budget, with six more routes than when it last tripped.

## 6. A deferred test is an unrun test

W3-T4 wrote §6.7's rows against routes W3-T1 and W3-T2 were still building, ran
what it could, and returned the rest as `deferred` with their exact titles —
which was the right call, and is why they cost an hour at integration instead of
turning up in production. What running them found is the point:

**One was a wrong selector.** The wizard opens on its TOOL CHECKLIST (§6.5), so
nothing carries `data-step-key` until "commencer" is pressed, and the verdict
buttons live in the sticky bar rather than inside the step. Written blind, the
helpers reached for the step directly.

**One was a missing product behaviour.** §6.7 asks that `?parts=` naming nothing
this bike has falls back to a full checkup **and says so**. The fallback
happened in silence: a visitor who asked about their brakes got a twelve-
question checkup with no explanation.

**And one was a rule that could not fire at all.** §5.4's "a later OK on a part
with an open item marks it `done` with `reason: 'recheck-ok'`" existed as a pure
function (`markRechecked`), a unit test, and an e2e row — and **had no
production caller on either path**. Two things kept it unreachable for a guest:

1. a finished checkup was always resumed, so coming back could only edit the
   same checkup — and changing a verdict there DROPS the line (the visitor
   withdrew the finding) rather than closing it (the bike answered differently a
   month later);
2. `mergeGuestBuildList`, written earlier in this same integration, pruned every
   line the new checkup did not derive. Correct for a re-run, wrong for a later
   checkup: it deleted findings nobody had contradicted.

The server never had either problem, and the reason is worth keeping: it holds
one `BuildList` per `Checkup`, so "prune what this checkup no longer finds"
(`writeBuildList`) and "close what a later checkup contradicts"
(`closeRecheckedItems`) are naturally different operations on different rows. A
guest has one key per bike, so the distinction had to be carried explicitly —
`StoredBuildList.checkupId`, and a `sameCheckup` branch in the merge.

**The general shape**: when one side of a system collapses two cases into one
storage slot, the rule that distinguishes them has to be written down, because
nothing else will. And the e2e row that was supposed to catch all of this read
the wrong localStorage key, so it could never have passed — it was deferred, and
a deferred test proves nothing at all.

## 7. One acceptance criterion the repository cannot meet as written

§6.8 AC2 asks that `npm run build` mark `/[locale]`, `/[locale]/guides/[slug]`
**and `/[locale]/velo/demo`** static. The first two are (`●` in both locales,
and that is what AC2 exists to prove — the `<Suspense>` boundaries hold). The
third is not, and cannot be: `/[locale]/velo/[id]` builds `ƒ`.

This is a W2 decision, recorded in `CLAUDE.md` and `.debug/006`, and it is
load-bearing in two directions. `generateStaticParams` for `demo` puts **every**
UUID into Next's on-demand static mode, where reading the session is
`DYNAMIC_SERVER_USAGE` — a 500 on every saved bike. A `loading.tsx` streams the
response, so the `notFound()` for a foreign bike can no longer set a 404, which
§6.7 requires.

Raised here rather than worked around: AC2's third clause and §4.7's
"another user's bike answers 404" cannot both hold on one route, and the plan
does not say which wins. W3 kept the 404.

## 8. Two failures that were not W3's, and how that was established

The full host matrix came back with eight failures, in two groups, and neither
was a W3 defect. Both are worth the paragraph because the method is the point.

**`seo.spec.ts` robots.txt, four projects.** `Sitemap:` pointed at `:3000`
instead of `:3100`. Cause: an ad-hoc `npx next build` run to inspect the route
table, without `NEXT_PUBLIC_SITE_URL` — so the artifact Playwright then reused
had the wrong origin baked in. `.debug/004 §10` recorded exactly this trap for
Lighthouse; it applies to every local e2e build. Rebuilt with the full
environment, the four pass. `scripts/ci/build.sh` sets the variable; a build run
by hand does not.

**`reduced-motion.spec.ts`, three projects.** Deterministic, not contention:
four repeats gave `3` every time. It looked like W3, because
`components/bike/BikeWorkspace.tsx` was the one bike3d-adjacent file the wave
touched — but that spec opens `/dev/bike3d`, which `BikeWorkspace` is not part
of, and `git diff --name-only` confirms nothing under `lib/bike3d/**` or
`components/bike3d/**` changed.

Settled by building **`5748bf9` — pre-W3 `main`** in a spare worktree and
running the same spec: it fails identically. The test infers "the camera
animated" from rendering at least five more frames in 1.2 s than the
reduced-motion run does; on this Mac after a long session both halves draw three
frames and the comparison measures nothing. CI's Linux Chromium has passed it at
every wave. The real fix — assert the camera's own state rather than a frame
count — is in `docs/backlog.md` for W4-T2, which owns the perf tier.

**The method**: when a test fails after a merge, the cheap question is not "what
in the diff could cause this" but "does it fail without the diff". A worktree at
the previous commit answers it in five minutes and is the only answer that does
not rely on reasoning about code you have just written.
