## 1. `NEXT_PUBLIC_TEST_HOOKS` never gated anything (§3.6 AC7 violated)

**Symptom.** A new build-output guard, run for the first time on a plain
`npm run build` (no flags), found the e2e remote control in the shipped JS:

```
✗ no test hooks — 1 hit(s)
  .next/static/chunks/3-clkjdzr5pm_.js
```

with the whole object inlined — `return function(e,t=window){return t.__va=e,…}`
followed by `{bike:{get ready(){…}}}`: `focus(id)`, `loseContext()`,
`materialOf(id)`, `setQuality()` — everything Playwright uses to drive the
viewer, downloadable by any visitor.

**Why.** `components/bike3d/BikeViewer.tsx` gates the probe the documented way:

```ts
const PerfProbe =
  process.env.NEXT_PUBLIC_TEST_HOOKS === "1"
    ? dynamic(() => import("./perf/PerfProbe"), { ssr: false, loading: () => null })
    : null;
```

**Next only inlines a `NEXT_PUBLIC_*` variable that exists in `process.env` at
build time.** Unset is not replaced with `undefined` — it is left as a runtime
property lookup on the client's `process.env` shim. So the ternary is not a
constant expression, nothing is constant-folded, and the `import()` stays in the
module graph. At runtime the lookup yields `undefined`, `PerfProbe` is `null` and
the probe never mounts — which is exactly why this was invisible: the app behaves
correctly, the _code_ ships. Every gate of this shape was affected, and the
comment in `lib/testing/e2e-hooks.ts` asserting "a production build therefore
contains no hook code" had never been checked against a build.

It had also never been checked in CI _by construction_: the `build` job sets
`NEXT_PUBLIC_TEST_HOOKS: "1"` because its `.next` artifact is what the e2e matrix
downloads. The only builds with the flag off were local ones and Vercel's.

**Fix.** Normalise the flag to a literal in `next.config.ts`, so the comparison
is `"0" === "1"` and the import is dropped with the branch:

```ts
env: { NEXT_PUBLIC_TEST_HOOKS: process.env.NEXT_PUBLIC_TEST_HOOKS === "1" ? "1" : "0" },
```

**How a regression is detected.** `scripts/bundle-guard.ts`, over every `.js`
under `.next/static`, run after every build (`scripts/ci/build.sh` and
`scripts/vercel-build.sh`):

1. no `new Function(` / `eval(` — MDX is compiled at build time and `script-src`
   has no `unsafe-eval` (§5.8 AC1). `tests/security/xss-form-inputs.test.ts`
   greps our own _source_; this catches a **dependency** that bundles one.
2. `window.__va` present **iff** `NEXT_PUBLIC_TEST_HOOKS=1` — both directions, so
   "absent" is only ever asserted by a check known to be able to find it.

Verified both ways on real builds: flag off → 37 files, 0 hits (it was 1 before
the fix); flag on → 39 files, marker found. CI exercises the present direction
(the build job sets the flag); `npm run ci:local` and Vercel exercise the absent
one, and on Vercel the guard blocks the deploy.

**Lesson.** A gate whose failure mode is silent is not a gate until something
asserts the output. "Only X imports it and X is conditional" is a claim about the
bundler, and bundler behaviour is a (verify) fact — check it against the build.

## 2. `--strict` was documented as on, and was wired nowhere

`lib/content/check.ts` documents `--strict` as "run from W2-T4 on and always in
CI"; `scripts/ci/content.sh` carried the comment "W2-T4 turns on `--strict`";
plan §8.3 makes it W2-T4a's acceptance. Nothing passed the flag: not
`package.json`'s `content:check`, not the CI content step. The W1 unit test even
pinned the _opposite_ — `expect(runCli([…, "--strict"]).code).toBe(1)`, i.e. "the
corpus does not pass strict yet", which is how the gap survived W1.

With the full corpus merged, strict passes: **47 guides, 222 steps, no problem.**
So `content:check` and `scripts/ci/content.sh` now pass `--strict`, and the test
asserts `0`. The ★ rules this turns on: every rendered part covered by a check
step, ≥ 40-word check questions in both locales, safety entries on e-bike and
brake guides, `brands.yaml` tiers, `related`/`ko` targets resolving.

## 3. Three W1 test files, two content tasks, one merge

T4a and T4b both had to repair the W1-T4 tests that hard-coded the 3-guide W1
corpus (`check.test.ts`, `guides.spec.ts`, `guides-filter.spec.ts`) — the only
conflicts of the whole wave, and predictable from the file lists.

Resolved toward **T4b's corpus-following** assertions: the tests read
`content/guides/` and follow whatever is there, so the corpus can keep growing
without touching them again. T4a's sortedness assertion was kept alongside T4b's
`slugsOnDisk()` equality (it costs nothing and pins a different property), and
T4a's `buildBikeSpec(answerWithDefaults(BIKE_PRESETS[…]))` survives as
`specFor()` in `tests/_fakes/domain/build.ts`, which is the same expression
extracted.

One trap worth naming: git's line-based merge produced a **duplicate
`import { matchesSpec }`** in `guides-filter.spec.ts` — both sides added the same
import in different positions, so neither side's hunk conflicted and the file was
left with two. It is a `tsc` error, not a silent bug, but a "resolve the markers
and move on" pass would have shipped it.

## 4. The decision tree drew numbered callouts and never said what they meant

T4c's 16 help drawings carry numbered `data-callout` marks, and
`messages/{fr,en}/illustrations.json` carries `callouts.<n>` for 30 ids. Guides
rendered the legend (`components/mdx/Illustration.tsx`); the decision tree's help
panel rendered the drawing alone — circled numbers on a frame with nothing naming
them, which is worse than no callouts for a screen-reader user and useless for
everyone else.

The legend now renders in `HelpFigure` inside
`components/decision-tree/tree-illustrations.tsx` — server-side, so the barrel
and the catalogue stay out of the client bundle and the tree still receives
already-rendered nodes. Same a11y shape as the guide renderer: an `aria-hidden`
badge carrying the number for sighted matching, and an `sr-only` `"2. "` prefix
so the list reads correctly aloud.

Regression test: `HelpDisclosure.test.tsx`, "names every numbered callout of the
drawing", both locales, asserting badge and read-aloud text per item, with a
`checked > 0` guard so a registry that lost its callouts cannot pass vacuously.
**Mutation-verified**: reverting the wiring fails it (2 failed), restoring passes.

## 5. `PLAYWRIGHT_PORT` moved the server but not the URLs

`playwright.config.ts` derives `PORT` from `PLAYWRIGHT_PORT` (one server per
worktree) but read `AUTH_URL` / `NEXT_PUBLIC_SITE_URL` as
`process.env.X ?? BASE_URL` — _after_ `loadEnv(".env.test")` had put
`http://localhost:3100` into `process.env`. A worktree on 3101 therefore served
on 3101 and minted Auth.js callbacks for 3100: sign-in redirects land on another
worktree's server.

Fixed by capturing the two variables **before** `loadEnv` and using only those:
the shell may still override (a tunnel, a preview), the committed file may not.

## 10. What the first CI run caught (2026-09-18)

`bash scripts/ci.sh` + the full local Playwright matrix were green on `7149e47`,
and CI still came back **red on three jobs from two causes**. Both are recorded
in full in their own notes; what belongs here is why local green was not enough.

| Job                      | Cause                                                      | Note |
| ------------------------ | ---------------------------------------------------------- | ---- |
| `e2e (mobile-chromium)`  | `Input.synthesizeScrollGesture` is inert on Linux Chromium | 005  |
| `e2e (mobile-landscape)` | the same test, same cause                                  | 005  |
| `lighthouse`             | home LCP 3.6 s / TBT 336 ms — **two** independent faults   | 007  |

**The pattern worth keeping.** Every one of these was invisible to the gates
this repository runs before a push:

- the touch failure needed a **different browser build** (Linux + SwiftShader).
  The W2 task branches were never pushed, so that spec had never once run on CI.
  `scripts/ci/e2e-docker.sh` now makes that environment reachable locally.
- the Lighthouse failure needed **CI's slower machine**: the same build measured
  TBT 336 ms there and ~40 ms on this Mac. LCP did reproduce locally, which is
  what made the diagnosis possible at all.
- W2-T3's routes entered the Lighthouse URL list only once its page file
  existed, so `/velo/demo` was audited for the first time at integration — and
  immediately failed an SEO assertion it can never satisfy, because §6 requires
  it to be `noindex`.

**Two gate constants were stale rather than wrong-at-the-time**, and both failed
for reasons unrelated to the change under test: `resource-summary:script:size`
(560 000, derived when home first-load was ~130 kB) and the absent
`NEXT_PUBLIC_SITE_URL` in local builds, which made every local `npm run lhci`
fail `categories.seo` with canonicals for the wrong port. Both are now derived
from a single source instead of pinned by hand.

**A cost paid twice.** Mounting sonner's `<Toaster/>` in the locale layout — a
three-line change to finish §6.7's toast — added 8.5 KiB gzip to _every route in
the site_. It was caught only because the ratchet is measured on the merged tree
after every wave, not per branch. A layout import is paid by every page: that is
the lesson, and it is now in `CLAUDE.md`.
