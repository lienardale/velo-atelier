# 014 — W4-T2: what the perf tier measured, and why the bike page's LCP was a status line

**Date** 2026-09-21 · **Status** one cause fixed (EN bike LCP), two findings open
(bike TBT, SwiftShader raster) · **Branch** `w4/t2`

The machinery this wave added (soft tier, baselines through a bot PR, the
per-run Lighthouse table, the bundle breakdown) is described in
[`docs/bike3d-perf.md`](../docs/bike3d-perf.md). This note keeps what the
numbers said, and the things that were not obvious.

## 1. `/en/bike/demo`'s LCP was the 3D loading notice

**Symptom.** The first five-run nightly on the branch (perf.yml run
35600024232, `ec56fb5`), applied throttling, 412 × 915 at DPR 2.625:

| URL             | perf (5 runs)            | LCP ms (5 runs)          | TBT ms (median) |
| --------------- | ------------------------ | ------------------------ | --------------- |
| `/fr/velo/demo` | 0.74 0.75 0.76 0.74 0.74 | 2309 2314 2302 2286 2299 | 919             |
| `/en/bike/demo` | 0.61 0.60 0.62 0.60 0.60 | 4464 4524 4464 4564 4520 | 920             |

The same page, the same code, the same TBT — and 2.2 s of LCP between the
locales, every run.

**Cause.** The LCP element is the largest text painted before any input, and a
later text replaces the candidate if it is larger. The workspace's `<h1>` is
painted at first paint; the viewer's `bike3d-notice` gets "Loading the 3D
view…" when the 3D chunk starts mounting, which on CI waits for hydration and
the idle callback. Measured on macOS with both web fonts loaded (range rects):

| text                       | EN px² | FR px² |
| -------------------------- | ------ | ------ |
| `<h1>` (demo bike's name)  | 2589   | 5675   |
| loading notice (`text-sm`) | 2489   | 3055   |

EN's two are 4 % apart, so a font-metric difference decides it; FR's `<h1>` is
twice the notice. On CI's Linux fonts the EN notice won.

**Reproduction.** The pre-change build served with `Demo bike` → `VTT` in the
HTML and its RSC payload alike (no hydration mismatch, no console error) —
what a user's bike named "VTT" is in any locale — moves its LCP, run after run,
from the first-paint `<summary>` "Frame and fork" (2223 px²) to
`p[bike3d-notice]` "Loading the 3D view…" (2646 px²) at the 3D mount.

**Fix** (`d9836ac`). The loading notice stays in the same `role="status"`
live region with the same text, `sr-only` while it is the transient loading
one: announced, never painted. The no-WebGL, context-lost and error notices
stay visible. `tests/bike3d/bike-viewer.test.tsx` pins both sides
(mutation-checked).

**After** (perf.yml run 35606491888, `d9836ac`, five runs each):

| URL             | perf (5 runs)            | LCP ms (5 runs)          | TBT ms (median) |
| --------------- | ------------------------ | ------------------------ | --------------- |
| `/fr/velo/demo` | 0.78 0.80 0.79 0.79 0.79 | 2195 2189 2170 2154 2188 | 713             |
| `/en/bike/demo` | 0.78 0.79 0.79 0.78 0.78 | 2156 2179 2148 2191 2199 | 730             |

`/en/bike/demo`'s LCP fell 4520 → 2179 ms (−52 %) and its score 0.60 → 0.78,
while `/fr/velo/demo`'s LCP moved 2302 → 2188 ms (−5 %) — the size of this
runner being faster than the first one, which is also what the TBT column
shows: home went 258 / 224 → 148 / 148 ms with no change to home at all.
**So the two nightlies of one day differ by 20–40 % in TBT**: the bike pages'
919 / 920 against 713 / 730. The report's rule proposes TBT 1100 → 850 from
the second run, and the first run would fail 850. At integration, take the
TBT pin from the worse of the nightlies available (920 × 1.15 → 1100, no
change) until several nights give a spread. Performance (→ 0.70) and LCP
(→ 3000) come from the post-fix run; the slow run's French page, which the fix
does not touch (0.74, 2302 ms), would give 0.69 and 3000 — on a slow night the
bike bar still lands on, or 0.01 under, §7.3's target.

## 2. §6.8 AC9's "LCP element is the silhouette" cannot hold as written

Chrome's LCP considers `<img>`, `<image>` inside an `<svg>`, video posters,
background images and block-level text — never an inline `<svg>` of paths.
The silhouette (`BikeSilhouetteSvg`, one `<g role="button">` per part) is
therefore not a candidate, and the LCP element of `/fr/velo/demo` is the
`<h1>`, painted in the same first frame. The criterion's intent — the first
paint is the server-rendered page, not the canvas — holds; its letter would
need the silhouette drawn as an `<image>`, which the per-part buttons rule out.

## 3. Where the bike page's TBT goes (≈ 920 ms on CI, target 600)

Fresh browser per run at Lighthouse's profile (4× CPU, 562.5 ms RTT,
1.6 Mbit/s), CI GL flags, long tasks between FCP and the first 5 s quiet
window, attributed by the script each task ran (local, M2):

| phase                        | long tasks (ms)                                    |
| ---------------------------- | -------------------------------------------------- |
| hydration (react-dom chunk)  | eval 97–123, then 2–3 tasks of 57–97               |
| 3D chunk evaluation          | `02oq8oc908uc9.js` 82–139, `43clb_54po9xu.js` ≈ 65 |
| scene build + shader compile | 117–199 (one `FunctionCall` in three)              |
| first 3D frame               | 74–84                                              |

With WebGL disabled (`--disable-webgl`) the same page measures TBT 60–83 ms
over three runs: the 3D mount is most of the bike page's TBT. Not changed
here, because every lever is outside `BikeViewer`'s mount timing or would only
move the work out of Lighthouse's window (deferring past TTI's 5 s quiet
window hides the tasks, it does not remove them):

- `renderer.compileAsync(scene, camera)` instead of `compile` in `BikeScene`
  — three 0.185.1 polls `KHR_parallel_shader_compile`
  (`WebGLRenderer.js:1487–1527`), so program linking leaves the main thread;
- building the scene across frames instead of in one task;
- hydrating the parts panel lazily on mobile (`BikeWorkspace` / `PartsPanel`).

## 4. SwiftShader holds the first paint of a cold browser

A trace of a fresh Chromium with the CI GL flags: the renderer's main thread
sat 2.1 s in `WidgetBase::Shutdown → LayerTreeHost::~LayerTreeHost →
ProxyMain::Stop`, the compositor in `CommandBufferHelper::Finish →
GpuChannel::WaitForGetOffsetInRange`, and the GPU process in
`RasterDecoderImpl::DoEndRasterCHROMIUM` for 1.75 s — the page's first frame
rastered through software GL (`--ignore-gpu-blocklist` lets Chrome
GPU-rasterise on SwiftShader). FCP was the end of that task.
`--disable-gpu-rasterization`, as a diagnostic only, took cold FCP from
4.4–9.7 s to 1.6–2.1 s on the bike page and from 3.8–5.1 s to 2.0–2.1 s on
home (three to five cold runs per variant on this Mac during the wave, not
interleaved, so the direction is solid and the sizes are not).

On CI's idle runner every other URL's LCP lands at 1.75–1.97 s (home, the
guides, `/connexion`, `/acheter`; five runs each) and `/fr/velo/demo`'s at
2.29–2.31 s, and that is the table that decides. Locally the software raster
competes with every other build for the CPU: an `lhci` run at a load average
above 10 reported `/fr` at 0.57 / 0.91 / 0.66 with LCP 9.1 / 2.7 / 5.5 s,
where the nightly measured 0.93–0.95 and 1.82–1.87 s. The same command at a
load average of 4, on `d9836ac`, passed every assertion (`/fr` 0.96 at
2204 ms, the bike pages 0.86–0.87 at 3004–3027 ms with TBT 155–159 ms). The GL flags stay: they
are what makes the bike page render WebGL in CI, and changing them would
change what every Lighthouse number means.

## 5. On a real GPU, rAF intervals cannot answer "does a frame fit in 16.7 ms"

Headless Chromium 1.63 on an M2 renders on "ANGLE Metal Renderer: Apple M2"
with `--ignore-gpu-blocklist --enable-gpu` and on SwiftShader without them,
so the local GPU gate needs no headed window. But `requestAnimationFrame`
intervals there are pinned to the display: an **empty** page measures p95
16.8–18.8 ms (headless and headed, with or without
`--disable-frame-rate-limit`). The soft tier therefore records frame COST —
`gl.render` plus a one-pixel `readPixels`, which returns once the GPU has
finished — and keeps the intervals only for `longFrames`. The one-preset GPU
smoke on the `d9836ac` build: `gravel-1x11` p50 1.8 ms, p95 2.1 ms.

## 6. The baseline bot PR ran the repository's git hooks

The `perf baseline PR` job of run 35600024232 staged both baselines (7 presets
× 5 repetitions each, Prettier-clean) and failed in create-pull-request:
`npm ci` had run husky's `prepare`, so the bot's `git commit` ran
`.husky/pre-commit`, whose `tsc --noEmit` cannot pass in a checkout that never
generated `lib/content/generated`. Generating it would run project code in a
job holding a write token. `27686f1`: `HUSKY=0` and
`npm ci --ignore-scripts` in that job.

## 7. Pre-push refusals were the machine, not the code

Twice the pre-push `scripts/ci.sh` refused `w4/t2` on unit tests timing out at
5000 ms: nine tests at a load average of 10–45 (four agents and an amd64
container), then one (`PasswordStrength`, which imports zxcvbn's dictionaries
dynamically) with the 1-minute load at 39.8 during the coverage run and
`test-unit` taking 212 s. That file passes alone in 1.4 s; the next push, at
load 5, passed every step with `test-unit` in 44 s. No timeout was changed.
