### 3.4 The build-time preflight, and what `vercel-build.sh` now refuses

**The gap** [R]. With `npx`/`npm` stubbed, the previous `vercel-build.sh` under
`env -i VERCEL_ENV=production ENABLE_TEST_PAGES=1 NEXT_PUBLIC_DEMO_LOGIN=1` and
no `POSTGRES_*`, `AUTH_*` or `NEXT_PUBLIC_SITE_URL` printed
`▶ prisma migrate deploy (VERCEL_ENV=production)`, ran the migration, the build
and the bundle guard, and exited 0. `register()` is skipped during a build
(§3.1), so a scope's VALUES were first evaluated by the deployed server — after
promotion, after the production migration — and a pull request's preview only
evaluates the Preview scope.

**The order now** (`scripts/vercel-build.sh`): (1) `VERCEL_ENV` must be
`production | preview | development`; (2) `NEXT_PUBLIC_TEST_HOOKS` off
(`1 | true | yes`, any case, is on); (3) `npx tsx scripts/check-env.ts`; (4)
`npx prisma migrate deploy` only when `VERCEL_ENV=production`, then
`npm run build`, then `npx tsx scripts/bundle-guard.ts`. Steps 1–3 each exit 1
before anything is migrated or built.

The second line ends every refusal. The message is built from zod's issue paths
and messages: names and rules, never a value (pinned with a canary secret in
`tests/unit/deploy/vercel-build-guard.test.ts`,

- **A missing variable hides the cross-field rules.** zod skips `superRefine` on
  a type-level issue (a missing key, a non-numeric `BCRYPT_COST`); a too-short
  secret, a scheme-less URL, a non-postgres URL or an out-of-range cost do not
  hide them ([I], and the table). `parseEnv` is unchanged by ruling —
  `lib/env.ts` differs from the branch's previous commit in comments only [I] —
  so `check-env` says "the next build may name more" instead.
- **`check-env` has one caller.** Not `npm run build`, not
  `scripts/ci/build.sh`: CI builds without a production secret
  (`tests/unit/deploy/migrate-on-deploy.test.ts`,
  `keeps the contract preflight out of every build that is not Vercel's`). CI's
  contract is not weaker for it: `instrumentation.ts` evaluates it on every
  `next start` CI does (boot check, boot tier, Playwright's web server,
  Lighthouse).
- **The contract is stricter than what merely works.** Auth.js accepts any
  non-empty secret (`node_modules/@auth/core/lib/utils/assert.js:59`,
  `if (!options.secret?.length)`), the contract wants 32 characters;
  `lib/db/env.ts` trims the database URLs, the contract anchors
  `^postgres(ql)?://` on the raw value. By NAME all three scopes parsed ([R],
  [I], [D]); nobody on the branch could see the values. The first production
  build was the first evaluation of Production's values, and it passed (§3.10).
  A refused value fails that BUILD; the fix is the value, never the rule.

### 3.9 Prisma: the limiter's expected miss, counted, and where the marker is read

**Event shape** (read, `node_modules/@prisma/client/runtime/client.js`, 7.10.0):
`logEmitter.emit("error",{message:r.message,target:t.clientMethod,timestamp:new Date})`
inside `handleAndLogRequestError` — at the THROW site, with no error code. With
`"error"` or `{ emit: "stdout", level: "error" }` in `log`, Prisma registers its
own listener, which ends in `console.log("prisma:error", message)`: stdout, TWO
arguments, no `[prisma]` prefix.

**How many** [I], real PostgreSQL (`velo_atelier_w5fin_test`), an own client
that keeps its events, injected clock, identical under `NODE_ENV=production` and
`test`:

```
no row yet:                    events=2 targets=["authAttempt.update","authAttempt.update"] allExpected=true result={"ok":true,"retryAfterMs":0,"count":1}
window still open:             events=0
window still open (again):     events=0
window expired:                events=1 targets=["authAttempt.update"]
three fresh buckets (a first sign-in): events=6 … allExpected=true
```

So: **two P2025s per fresh key** (`bump()` and `reopen()` both miss —
`lib/security/rate-limit.ts:91` and `:99`), **one per expired window**, none for
an open window, **up to six on a first sign-in** (three buckets:
`lib/auth/authorize.ts:147-155`; "up to" because the per-IP limiter is the
allow-all one for a local address outside production). The first version wrote
"one per fresh key" and listed "a key whose window is still open" as a miss;
both were wrong. [R] counted the same on PGlite behind the real adapter.

### 4.8 Concurrency, the timeout and Neon — documentation, not observation

**Concurrency.** Per GitHub's documentation ([R], fetched 2026-10-06) a
concurrency group holds one run in progress and one pending, and a newly queued
run replaces the pending one. So `cancel-in-progress: false` means never
cancelled in flight and never two at once, NOT "every later migration queues".
Harmless between pushes to `main`; a mistaken `--ref <branch>` dispatch can
displace a pending `main` run and is then refused by the script. `queue: max`
exists in the same documentation and was not adopted: nothing here could
validate it short of a real dispatch. The first version asserted the block
nowhere (`cancel-in-progress: true`, the block deleted, a per-run group: 51/51
green); it is now a `toEqual` on the parsed value.

**The timeout.** `timeout-minutes: 10` bounds a hung connection or DDL. It does
not bound Prisma's advisory-lock wait: the pinned engine carries "Timed out
trying to acquire a postgres advisory lock (SELECT
pg_advisory_lock(72707369)). Timeout:" ([R], [I]: `strings` on the schema
engine; the length was not checked). The same engine carries "migrate found
failed migrations in the target database, new migrations will not be applied" —
a run killed mid-migration may need `prisma migrate resolve`. Not reproduced.

**Neon** ([R], Neon's documentation fetched 2026-10-06, paraphrased). A reset
from parent replaces the child's data AND schema with the parent's; the branch's
connection details do not change. A child branch's roles have the parent's
passwords by default; a child's own passwords are preserved across a reset only
from a PROTECTED parent, and protected branches are a paid-plan feature. The
project is on the Free plan (`docs/deploy.md`, "What W5 did"). Consequences
written into `docs/deploy.md` §1 and §4.5, each marked there:

1. "Resetting `preview` from its parent is still the one-click equivalent of a
   migration" was wrong: it copies production's rows into the database every
   pull request's preview reads.
2. After a reset the rotated `preview` password is EXPECTED to revert to
   production's (inferred from the two pages read together; not observed). Order
   afterwards: re-rotate, GitHub secret, both Vercel scopes, redeploy previews,
   dispatch.
3. Before the rotation the preview string carries production's password — and
   `.debug/016` §3 records both endpoints being queried by hand in the W5
   session. Rotating `preview` does not change `production`'s password. Whether
   to rotate production's is the maintainer's decision; it was not checked
   against the live project and nothing here did it.
4. Not observed, per Neon's Prisma guide as summarised to a reviewer: an idle
   compute can outlast Prisma's connect timeout, so a first run red on P1001 may
   be a cold start.

### 5.1 `npm run lhci` and `npm run ci:local` lose node under nvm, on this machine

**Symptom.** Both exit 127, `npx: command not found`.

**Root cause.** Under `npm run`, npm exports `npm_config_prefix`.
`scripts/ci/_lib.sh` sourced `~/.nvm/nvm.sh` whenever the file existed; nvm
prints

```
nvm is not compatible with the "npm_config_prefix" environment variable
```

and removes node from `PATH` (this machine's nvm directory is a symlink to
another volume). Calling the scripts with `bash` directly works — and that is
how CI and the git hooks call them, which is why nothing had shown it.
`ci:local` was already affected before 2026-10-06; `lhci` became affected when
PR #16 routed it through the script (§3.8).

**Fix**, in the close-out change that carries this note: `scripts/ci/_lib.sh` no
longer sources nvm when a Node of the right major is already on `PATH` — which
is every `npm run` started on Node 24, since npm is running on that Node. It
reads the major of the `node` it finds and reaches for nvm only when there is
none or it is not 24: under a Node of another major it still sources nvm, and
the old failure is unchanged there. When it does source nvm it passes
`--no-use` and then runs `nvm use --silent 24`, so `nvm.sh` no longer inherits
the step script's positional parameters.

`tests/unit/deploy/lib-nvm.test.ts` (four cases, a stand-in `nvm.sh` in a
sandbox `HOME`) executes both directions: the right Node on `PATH` → nvm not
sourced and node still reachable; no Node → sourced; another major → sourced;
sourced with `--no-use` and never the caller's arguments. Each of two mutations
(always source; drop `--no-use`) fails one case.

## 6. How to detect a regression

**§2, advisories.**

- `npx audit-ci --config audit-ci.json` (CI's `audit` job) and
  `bash scripts/ci/trivy.sh`. On a day ids are landing, run `audit` more than
  once before believing a green (§2.6).
- `sprintf-js` coming back turns `audit` red: that is what the scoped override
  is for. `npm explain js-yaml@3.15.2` shows the override in force.
- Renovate's Dependency Dashboard (issue #11) is where a proposal against an
  `overrides` entry appears (§2.5).

**§3, the environment contract.**

- `npx vitest run --project unit tests/unit/db tests/unit/deploy` — the
  contract's rules, `check-env`, `vercel-build.sh`'s refusals, the `[env]` line,
  the boot tier's link to the gate. No network, no database.
- `ENABLE_TEST_PAGES=1 NEXT_PUBLIC_TEST_HOOKS=1 bash scripts/ci/build.sh` — ends
  with the boot check and `npx --no-install vitest run --project boot`. Needs a
  reachable `_test` database, and tests the build it has just made (§3.7).
- `npx vitest run --project integration tests/integration/prisma-error-log.test.ts`
  — nothing about the limiter's expected miss on any console channel.
- On Vercel: the build log must carry
  `check-env: environment contract satisfied (VERCEL_ENV=<scope>, isProduction=<…>).`
  and the runtime log `[env] contract enforced (VERCEL_ENV=<scope>)`. A build
  that stops on `✗ VERCEL_ENV is not set` means the system-variables checkbox is
  off. `/api/health`: 200 is healthy, 503 is the database, a 401 on a preview is
  deployment protection, and **a 500 is the contract** (§3.2).

**§4, the two workflows.**

- `npx vitest run --project unit tests/unit/ci tests/unit/deploy` — the
  refusals, the success path, the summary, the workflow shapes, the validator's
  verdict. No network, no database.
- `npx vitest run --project integration tests/integration/migrate-preview.test.ts`
  — the real Prisma, green, on the tier's `_test` database.
- `bash scripts/ci/renovate-config.sh` — the real validator (seconds warm,
  ~350 MB cold).
- After a dispatch: `gh run view <run-id> --log`, and read `N migrations found`
  TOGETHER WITH Prisma's verdict under it. Then the two branches in the Neon
  console's SQL editor. `/api/health` cannot tell: it is a bare `SELECT 1`
  (`app/api/health/route.ts`), unchanged on purpose.

**§5, the launch checklist.**

- §5.1: `npx vitest run --project unit tests/unit/deploy/lib-nvm.test.ts`; and,
  on a machine with nvm, `npm run ci:local`, or `npm run lhci` after a build.
  Exit 127 with `npx: command not found` is this.

- §5.3: `npx vitest run --project unit tests/unit/content/check.test.ts` on its

  machine.
- §5.4: after an audit of production, the reports under `.lighthouseci/` must

- §5.6, finding 1:
  `npx vitest run --project unit tests/unit/deploy/dev-script.test.ts`. In a
