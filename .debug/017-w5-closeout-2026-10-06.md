### 3.4 The build-time preflight, and what `vercel-build.sh` now refuses

**The gap** [R]. With `npx`/`npm` stubbed, the previous `vercel-build.sh` under
`env -i VERCEL_ENV=production ENABLE_TEST_PAGES=1 NEXT_PUBLIC_DEMO_LOGIN=1` and
no `POSTGRES_*`, `AUTH_*` or `NEXT_PUBLIC_SITE_URL` printed
`▶ prisma migrate deploy (VERCEL_ENV=production)`, ran the migration, the build
and the bundle guard, and exited 0. `register()` is skipped during a build
(§3.1), so a scope's VALUES were first evaluated by the deployed server — after
promotion, after the production migration — and a pull request's preview only
evaluates the Preview scope.

**The order now** (`scripts/vercel-build.sh`): (1) `VERCEL_ENV` must be
`production | preview | development`; (2) `NEXT_PUBLIC_TEST_HOOKS` off
(`1 | true | yes`, any case, is on); (3) `npx tsx scripts/check-env.ts`; (4)
`npx prisma migrate deploy` only when `VERCEL_ENV=production`, then
`npm run build`, then `npx tsx scripts/bundle-guard.ts`. Steps 1–3 each exit 1
before anything is migrated or built.

### 3.9 Prisma: the limiter's expected miss, counted, and where the marker is read

**Event shape** (read, `node_modules/@prisma/client/runtime/client.js`, 7.10.0):
`logEmitter.emit("error",{message:r.message,target:t.clientMethod,timestamp:new Date})`
inside `handleAndLogRequestError` — at the THROW site, with no error code. With
`"error"` or `{ emit: "stdout", level: "error" }` in `log`, Prisma registers its
own listener, which ends in `console.log("prisma:error", message)`: stdout, TWO
arguments, no `[prisma]` prefix.

**How many** [I], real PostgreSQL (`velo_atelier_w5fin_test`), an own client
that keeps its events, injected clock, identical under `NODE_ENV=production` and
`test`:

```
no row yet:                    events=2 targets=["authAttempt.update","authAttempt.update"] allExpected=true result={"ok":true,"retryAfterMs":0,"count":1}
window still open:             events=0
window still open (again):     events=0
window expired:                events=1 targets=["authAttempt.update"]
three fresh buckets (a first sign-in): events=6 … allExpected=true
```

So: **two P2025s per fresh key** (`bump()` and `reopen()` both miss —
`lib/security/rate-limit.ts:91` and `:99`), **one per expired window**, none for
an open window, **up to six on a first sign-in** (three buckets:
`lib/auth/authorize.ts:147-155`; "up to" because the per-IP limiter is the
allow-all one for a local address outside production). The first version wrote
"one per fresh key" and listed "a key whose window is still open" as a miss;
both were wrong. [R] counted the same on PGlite behind the real adapter.

**The two formats** [I] (no `errorFormat` option; Prisma picks `minimal` when
`NODE_ENV === "production"`, `colorless` otherwise), `↵` standing for a newline:


### 4.8 Concurrency, the timeout and Neon — documentation, not observation

**Concurrency.** Per GitHub's documentation ([R], fetched 2026-10-06) a
concurrency group holds one run in progress and one pending, and a newly queued
run replaces the pending one. So `cancel-in-progress: false` means never
cancelled in flight and never two at once, NOT "every later migration queues".
Harmless between pushes to `main`; a mistaken `--ref <branch>` dispatch can
displace a pending `main` run and is then refused by the script. `queue: max`
exists in the same documentation and was not adopted: nothing here could
validate it short of a real dispatch. The first version asserted the block
nowhere (`cancel-in-progress: true`, the block deleted, a per-run group: 51/51
green); it is now a `toEqual` on the parsed value.

**The timeout.** `timeout-minutes: 10` bounds a hung connection or DDL. It does
not bound Prisma's advisory-lock wait: the pinned engine carries "Timed out
trying to acquire a postgres advisory lock (SELECT
pg_advisory_lock(72707369)). Timeout:" ([R], [I]: `strings` on the schema
engine; the length was not checked). The same engine carries "migrate found
failed migrations in the target database, new migrations will not be applied" —
a run killed mid-migration may need `prisma migrate resolve`. Not reproduced.

**Neon** ([R], Neon's documentation fetched 2026-10-06, paraphrased). A reset
from parent replaces the child's data AND schema with the parent's; the branch's
connection details do not change. A child branch's roles have the parent's
passwords by default; a child's own passwords are preserved across a reset only
from a PROTECTED parent, and protected branches are a paid-plan feature. The
project is on the Free plan (`docs/deploy.md`, "What W5 did"). Consequences
written into `docs/deploy.md` §1 and §4.5, each marked there:

1. "Resetting `preview` from its parent is still the one-click equivalent of a
   migration" was wrong: it copies production's rows into the database every
   pull request's preview reads.
2. After a reset the rotated `preview` password is EXPECTED to revert to
   production's (inferred from the two pages read together; not observed). Order
   afterwards: re-rotate, GitHub secret, both Vercel scopes, redeploy previews,
   dispatch.
3. Before the rotation the preview string carries production's password — and
   `.debug/016` §3 records both endpoints being queried by hand in the W5
   session. Rotating `preview` does not change `production`'s password. Whether
   to rotate production's is the maintainer's decision; it was not checked
   against the live project and nothing here did it.
4. Not observed, per Neon's Prisma guide as summarised to a reviewer: an idle
   compute can outlast Prisma's connect timeout, so a first run red on P1001 may
   be a cold start.

**What the fix is.**

- **One definition of the stored shape.** `lib/guest/schema.ts` no longer has
  a schema of its own for `va:checkup:local`: it reads the key through
  `peekStoredCheckup` (`lib/checkup/storage.ts`), i.e. `StoredCheckupSchema`,
  the wizard's. That read removes NOTHING — `readStoredCheckup`, the wizard's
  own, removes a value it cannot parse, which here would be the same data loss
  by another road.
- **The payload carries answers, not items.** A checkup in the `GuestState`
  contract is its `guestKey`, its scope with `partIds`, and `answers` /
  `symptoms` / `notes` keyed by step key, `startedAt`, `completedAt` — no
  step, and no part or guide per answer. `strictObject` at every level, each
  id matched by pattern at its column's length, a cap on every array and on
  each of the three records. `GUEST_STATE_VERSION` went from 1 to **2**, and
  that is not bookkeeping: the old collector sends `checkups: []` — a payload
  BOTH shapes accept — and then clears the key. Refusing version 1 makes a
  payload from it a `VALIDATION` that writes nothing and keeps every key.
  (Whether a tab loaded before a deploy can still reach the new action was not
  observed; this is the wall for the case where it can.)
- **The server re-plans** (plan §5.4). `importGuestState` derives the bike as
  before, plans it with `planForBuild` (`lib/content/checkup-plan.ts` — the
  plan `controle/actions.ts` now uses too, extracted from its `planFor`), and
  accepts the payload with `fromStored` / `reconcile`: an answer whose key is
  not in the plan is dropped, and so is a symptom the step does not offer. The
  rows are `answeredItems(state)` (`lib/checkup/items.ts`, extracted from
  `writeItems`, which uses it too). A checkup none of whose answers survives
  writes no row. (**Which plan**: the version of 2026-10-08 planned the SCOPE
  the payload named. Since 2026-10-09 it is the bike's FULL plan — "Found in
  review", R1.)
- **A COMPLETED checkup links and writes part states** (plan §4.2 b): the
  imported `BuildList.checkupId`; `checkupItemId` on every line whose
  `(action, partId)` `deriveBuildList(state)` derives; KO → `BROKEN`, OK →
  `OK` + `lastServicedAt`, SKIPPED → unchanged, on the part each item names.
- **One transaction per bike**, with the row ids the links need generated in
  Node. Before, the bike and everything under it were one nested `create`;
  the links need a list to point at a checkup created beside it, so the
  writes are now `$transaction([bike, …checkups, …lists])`.
- **The answer says what became of each checkup, and the browser clears on
  that answer only.** `GuestImportSummary.bikes[].checkups[]` is `imported`,
  `already-imported`, or `skipped` with a reason (`nothing-kept`,
  `bike-already-imported`, and since 2026-10-09 `other-bike`);
  `settleGuestImport` names the keys to forget — `va:checkup:local` only for
  the first two, or when there was nothing to import — and `clearGuestKeys`
  removes exactly those. `clearGuestState()` is gone. A checkup that stays is
  said to the visitor (`account.import.checkupKept.*`, FR and EN). (**What
  `already-imported` means** was the checkup's id until 2026-10-09 and is its
  content since — "Found in review", R2.)

**Choices made in the fix — decisions, not findings.**

- _An unfinished checkup links nothing._ Its row and items are imported; no
  `BuildList.checkupId`, no `checkupItemId`, no part state. Plan §4.2 b puts
  both under the COMPLETE action, and `saveCheckupAction` leaves an account's
  unfinished checkup the same way. Its `startedAt` is kept to the millisecond,
  so `existingCheckup` recognises the run: a FULL checkup resumed and finished
  on the account is the same `Checkup` row, and `finishCheckupAction` links
  the list then. (A PARTIAL one: see the paragraph after this list.)
- _`COMPLETED` if and only if the payload carries `completedAt`_ — and at
  least one of its answers survived the re-plan. `reconcile` also drops the
  date whenever today's plan asks a question the checkup did not answer; the
  import does not follow it there. A checkup finished before the corpus grew
  a question is still a finished checkup — for the wizard, which never
  resumes a stored checkup that has a `completedAt` (`isFinished`,
  `components/checkup/Wizard.tsx`), and for an account's own `COMPLETED` rows
  — and reopening it would hand a finished checkup to the resume path. The
  date is all the payload decides: the rows, the part states and the links are
  computed from the plan, for the answered questions only.
  `finishCheckupAction` is no stricter: it does not check that every question
  has an answer either (read in `controle/actions.ts`). The first session's
  draft of this fix took `reconcile`'s verdict instead; it was changed before
  anything was committed.
- _One part per item._ When an answered step reports on several parts (17 of
  the 34 steps of a full checkup on the gravel preset do — counted, [I]), the
  status goes to the part its `CheckupItem` row names — the step's first — and
  to no other: on that bike a full checkup reports on 24 parts and its rows
  name 18. Rule (b) maps an ITEM's result to a part state, and a row names one
  part; the import before this change did the same, with the part id the
  browser had resolved, which was also the step's first. Within one checkup a
  KO is never undone by an OK on the same part; before, the last answer won.
- _The import is NOT aligned with `finishCheckupAction`_, which writes a KO as
  `ATTENTION`, host-expanded through `statusByPart` (O3 below). That

### 5.7 The Linux container: one test fails one time in four, and the cause is in the page (2026-10-07)

`npm run e2e:docker -- --project=desktop-chromium --project=mobile-chromium`
— the amd64 CI image, emulated on Apple Silicon — on the build of `2a311e5`,
13:13Z–13:58Z [O]: **924 passed, 3 failed, 1 flaky, 64 skipped** in 44.8 min.
All 20 `@snapshot` comparisons passed, which is what this run is the only
local source of.

**Symptom.** The three failures and the flaky one are one test, in both
languages and both projects: `tests/e2e/guides-filter.spec.ts`, "a card opens
its guide". It goes to `/guides`, clicks the first card's link and expects the
guide's URL; `toHaveURL` timed out after 10 s with the URL still `/fr/guides`.
Run on its own with `--repeat-each=3 --retries=0`: 9 of 12 passed in about
3 s, 3 failed. It passed on the host the day before (431 and 874 tests) and in
CI's native Linux matrix on all five pull requests.

**Root cause — read in the source, not proven by an experiment.**
`app/[locale]/guides/page.tsx` renders
`<Suspense fallback={<GuideGrid guides={guides} />}>` around `GuideFilters`, a
client component that calls `useSearchParams()`. On a statically prerendered
route that is the shape `.debug/011` describes: the FALLBACK — the same grid of
cards — is what the HTML holds, and React builds the boundary again on the
client instead of hydrating it. The card a visitor sees first is therefore
replaced by a second, identical one, and a click that lands during the swap is
on a node that is going away. On a fast machine the window is too short to
hit; the emulated container makes it one in four.

**Fix.** None here. It costs a second tap on a slow device and loses nothing,
and the right fix is the one `.debug/011` made for the decision tree (read the
query without `useSearchParams` during render, so the list is hydrated rather
than rebuilt), which is a change to a page, not to a close-out.
`docs/backlog.md` has the entry.

**What it is not.** Not noise to retry past, and not a reason to loosen the
test: the test is right that a click on a visible card should open it.

### 5.8 The part edit form belonged to no part: one part's value written to another, and typed text dropped (2026-10-09)

**Root cause** — three things, none of which a test could see while every
test of the form rendered it with a part set by hand
(`components/bike/PartInfo.test.tsx`).

1. `PartInfo` rendered `<PartEditForm>` with no key, and the panel does not
   unmount when the selection changes, so React kept the same instance and
   the same `<input>` for the next part. An uncontrolled input does not follow
   a new `defaultValue` once it has a value of its own, and React gives it one
   at mount (`value === element.value || (element.value = value)`, read in
   react-dom 19.2.8, `react-dom-client.development.js:1720`; the run above is
   what it looks like). The per-field status lived in that same instance,
   keyed by attribute key alone.
2. The field committed on EVERY blur, whatever it held, with no comparison:
   a stale field was a write waiting for a focus.
3. A field removed while it has focus gets no `onBlur` from React (next
   paragraph), so the only exit that committed was a blur that reached React
   before the node went.

**What a real browser does when the next press is another tab** [I,
2026-10-09, a probe spec outside the repository; Chromium 153.0.8010.12
headless on macOS, the unfixed build of `1c22923` with the test hooks; a
guest bike, 45 typed in the front tyre's width and the field not left, then
the "Pièces" tab — and again "Actions" — pressed with the pointer]:

- `desktop-chromium`, a mouse click. Events at `document`, capture phase, in
  order: `pointerdown` and `mousedown` on the tab, the field still in the DOM
  and still `activeElement`; then **`change`, `blur` and `focusout` ON THE
  FIELD, the field still connected and `activeElement` already `<body>`**;
  then `focus` on the tab with the field gone; `pointerup`, `mouseup`,
  `click`. `va:bike:local` afterwards: `tire-front.etrto-width = 42`. **The 45
  was lost.** Four runs of four (two tabs, two languages).
- `mobile-chromium`, a tap: `pointerdown`, `touchstart`, `pointerup`,
  `touchend`, then the synthesised `mousedown` and the same `change`, `blur`,
  `focusout` on the field, then `focus` on the tab. Stored: 42. Four of four.
- The committed test of this case failed on that build for the guest bike AND
  for a saved one, whose row was read from PostgreSQL: 42 where 45 was typed.

So the loss the verifiers reproduced in jsdom is real in Chromium, and for a
reason their emulation had guessed: Radix activates a tab on `mousedown`
(`@radix-ui/react-tabs` `dist/index.mjs:123-125`, read), React commits the
change before the press's default action moves the focus, Chromium DOES fire
`blur` on the focused node as it is removed — and React ignores events that
arrive during its own commit (`_enabled = !1` as a commit starts, and
`dispatchEvent` does nothing without it: `react-dom-client.development.js`
lines 13861 and 23582, read). A browser that fired no `blur` at all would
lose the text the same way. Only Chromium is installed here: **WebKit and
Firefox were not run.**

One more thing a browser settled, as a by-product of the mutation runs below
[I]: with the removal flush disabled and everything else in place, 45 typed
for the front tyre followed by ONE click on the rear tyre's mesh still stored

therefore leaves the field before the click selects — the order the
verifiers could only read in camera-controls' source. On a touch screen it
was not observed: the helper lowers the sheet with the keyboard first.

**Fix.** The three rules below are in `components/bike/PartEditForm.tsx`. In
the first version (`620f72e`) that file was the whole change — nothing else
in `app/`, `lib/` or `components/`, tests aside — and this paragraph said so.
It went on saying so, with "`lib/bike/repo.ts` and `updateBikePartAction` are
untouched", through repairs that rewrote the action ("Second review", finding
1). As it stands the fix is also:

- `updateBikePartAction` (`app/[locale]/velo/[id]/actions.ts`), now one
  interactive transaction that takes the bike row's lock before it reads —
  the only interactive `$transaction` in `app/` or `lib/`. Its write path and
  its ways of failing (a wait on the lock, Prisma's transaction timeouts on a
  pool of three connections) are NEW, were read and not measured, and have
  not run on production ("Review of the fix", finding 2);
- `loadToast()` in `components/ui-ext/Notices.tsx`, and
  `components/bike/UnsavedNotices.tsx`, which `BikeWorkspace` mounts (finding
  3);
- `bikeParam` on every repo of `lib/bike/repo.ts`: which bike it writes

Three rules:

1. **The form is keyed by the part** — `PartEditForm` renders its fields
   under `key={partId}` INSIDE itself, not at the call site in `PartInfo`, so
   that no caller can forget it. A new part is a new instance: new inputs, an
   empty status map, and a `partId` that cannot change during an instance's
   life, which is what makes every write carry the part the field was
   rendered for, never the one selected when the write happens.
2. **A write needs an edit.** A number or text field records what was typed
   since its last commit (a ref set on every native `input` event and on
   React's `change` — by `onChange` alone until finding 1's own other case),
   and a blur commits only if there is such a record AND the value is not
   the stored one. Leaving a field unchanged sends nothing. The one exception
   is the one the old code had by accident and visitors may rely on: leaving
   a field whose last value was REFUSED sends it again. (Since the review:
   "the stored one" is what the form was last told, so the comparison is
   skipped while a write of the same field of the same bike has not answered
   — "Review of the fix", finding 4, and "Second review", finding 2.)
3. **Typed text is committed when the field is removed**, from a
   layout-effect cleanup, where the node is still in the document. It goes
   through a write of its own that touches none of the form's state — no
   status, no transition: the form is going too. What it commits is what
   leaving the field would have: the value typed, or a CLEAR for a field the
   visitor emptied. (Since the review: never text the browser cannot read as
   a number, which the first version sent as a clear — finding 1.)

Two things the three rules needed around them. A write that answers AFTER
its form is gone — rule 3's, or an ordinary save overtaken by the next
selection — has no field to report under: its build is still handed up
(`onSaved`), and a refusal is raised as a notice through the layout's toast
host, naming the part and the field, with the reason and for twenty seconds
(`bike.panel.unsaved`: "Pneu avant · Largeur du pneu : votre saisie n’a pas
été enregistrée."). Before, that refusal was shown under the NEXT part's
field of the same name, or nowhere. (Since the review: a toast TAKEN from
the host, which needs no download, in colours that pass AA, and said by the
page itself when no toast can be had — findings 3 and 9.) A write that does not answer at all is
still the route's `error.tsx` while its form is on screen, and that notice,
without a reason, once it is not. And an untouched field now FOLLOWS the
stored value when it changes under it (a second layout effect; text being
typed is never replaced): without it, the write of rule 3 answering after the
visitor has come straight back to the part left the old number in the field
beside a read-only line saying the new one — and the same after the panel is

## 6. How to detect a regression

**§2, advisories.**

- `npx audit-ci --config audit-ci.json` (CI's `audit` job) and
  `bash scripts/ci/trivy.sh`. On a day ids are landing, run `audit` more than
  once before believing a green (§2.6).
- `sprintf-js` coming back turns `audit` red: that is what the scoped override
  is for. `npm explain js-yaml@3.15.2` shows the override in force.
- Renovate's Dependency Dashboard (issue #11) is where a proposal against an
  `overrides` entry appears (§2.5).

**§3, the environment contract.**

- `npx vitest run --project unit tests/unit/db tests/unit/deploy` — the
  contract's rules, `check-env`, `vercel-build.sh`'s refusals, the `[env]` line,
  the boot tier's link to the gate. No network, no database.
- `ENABLE_TEST_PAGES=1 NEXT_PUBLIC_TEST_HOOKS=1 bash scripts/ci/build.sh` — ends
  with the boot check and `npx --no-install vitest run --project boot`. Needs a
  reachable `_test` database, and tests the build it has just made (§3.7).
- `npx vitest run --project integration tests/integration/prisma-error-log.test.ts`
  — nothing about the limiter's expected miss on any console channel.
- On Vercel: the build log must carry
  `check-env: environment contract satisfied (VERCEL_ENV=<scope>, isProduction=<…>).`
  and the runtime log `[env] contract enforced (VERCEL_ENV=<scope>)`. A build
  that stops on `✗ VERCEL_ENV is not set` means the system-variables checkbox is
  off. `/api/health`: 200 is healthy, 503 is the database, a 401 on a preview is
  deployment protection, and **a 500 is the contract** (§3.2).

**§4, the two workflows.**

- `npx vitest run --project unit tests/unit/ci tests/unit/deploy` — the
  refusals, the success path, the summary, the workflow shapes, the validator's
  verdict. No network, no database.
- `npx vitest run --project integration tests/integration/migrate-preview.test.ts`
  — the real Prisma, green, on the tier's `_test` database.
- `bash scripts/ci/renovate-config.sh` — the real validator (seconds warm,
  ~350 MB cold).
- After a dispatch: `gh run view <run-id> --log`, and read `N migrations found`
  TOGETHER WITH Prisma's verdict under it. Then the two branches in the Neon
  console's SQL editor. `/api/health` cannot tell: it is a bare `SELECT 1`
  (`app/api/health/route.ts`), unchanged on purpose.
