# 006 — `/velo/[id]`: four Next 16 behaviours that decided the route's shape

W2-T3, 2026-09-18. Next 16.3.4, React 19.2, next-intl 4.

Four findings, all discovered by `npm run build` + `next start` (never by `next
dev`, which disagrees with production on three of them). Together they explain
why `app/[locale]/velo/[id]/` has no `generateStaticParams`, no `loading.tsx`,
reads `searchParams` on the server, and exports only functions from its
`actions.ts`.

---

## 1. `generateStaticParams` on a route whose other params need the session

**Symptom.** `/fr/velo/demo` came out of `next build` prerendered (`●`) exactly
as §6.2 wants — and `/fr/velo/<uuid>` answered **500** in `next start`, with
`digest: 'DYNAMIC_SERVER_USAGE'` and nothing else in the log. In `next dev` the
same URL answered 404 correctly, which is why this survived the first pass.

**Investigation.** Bisected by emptying the segment: a trivial page with
`generateStaticParams` still 500s on an unlisted param; removing
`generateStaticParams` fixes it and costs the prerender.

| page                                      | `/velo/demo`    | `/velo/<uuid>` |
| ----------------------------------------- | --------------- | -------------- |
| `generateStaticParams: [{id:'demo'}]`     | `●` prerendered | **500**        |
| + `await connection()` in the `db` branch | `●` prerendered | **500**        |
| + `export const revalidate = 0`           | `ƒ`             | 404 / 200      |
| no `generateStaticParams`                 | `ƒ`             | 404 / 200      |

**Root cause.** With `generateStaticParams` present, Next renders a param the
list does not contain in its **on-demand static** mode, whose output it intends
to cache. Reading the session there (`cookies()` through `auth()`) is
`DYNAMIC_SERVER_USAGE`. `connection()` does **not** lift it in 16.3.4.

**Fix.** No `generateStaticParams` on `/velo/[id]`. The demo bike is
server-rendered per request; it still reads nothing about the request, and its
first paint is still the server-rendered silhouette.

**Consequence for the plan.** §6.8 AC2's "`npm run build` marks
`/[locale]/velo/demo` static (○/●)" is **not satisfiable** while the same route
serves saved bikes. The two ways to get it back, neither taken here: a separate
literal `app/[locale]/velo/demo/**` tree (duplicating `piece` and `reglages`
under it, against §1.1), or PPR.

**Regression detection.** `tests/e2e/part-panel.spec.ts` asserts 200 for a
fitted part and 404 for one that is not; the `/velo/<uuid>` path is covered by
the same spec's signed-in test, which would 500 the moment the enumeration comes
back.

---

## 2. `loading.tsx` makes `notFound()` answer 200

**Symptom.** `/fr/velo/nope`, `/fr/velo/<other-user-uuid>` and
`/fr/velo/demo/piece/e-motor` all answered **200** with the not-found page's
HTML. §6.7 and §4.7 want 404 (never 403, never 200).

**Root cause.** A `loading.tsx` in the segment makes the route stream. The
status line is on the wire before the page body runs, so the `notFound()` thrown
inside it can no longer set one.

**Fix.** No `loading.tsx` under `app/[locale]/velo/[id]/`. The page's own
fallback (`BikeCanvasFallback`) covers the visible loading state, and the
skeleton it wraps (`BikeCanvasSkeleton`) is still exported for any future
route-level loading file that does not gate a 404.

**Regression detection.** `tests/e2e/part-panel.spec.ts` →
"a part that is not on the bike is a 404".

---

## 3. `useTranslations()` in `loading.tsx` turns the whole segment dynamic

**Symptom.** Before #1 was understood: `/[locale]/velo/demo` was `ƒ` even with
`generateStaticParams`, and removing `loading.tsx` made it `●`.

**Root cause.** `loading.tsx` receives no `params`, so it cannot call
`setRequestLocale`. next-intl then resolves the locale from the request, which
is a dynamic read, and the segment loses its prerender. A `loading.tsx` with no
translations keeps it.

**Fix / rule.** A route-level `loading.tsx` must be **silent** — no
`useTranslations`, no `getTranslations`. `BikeCanvasSkeleton` exists for exactly
that and is documented as such.

---

## 4. A `"use server"` file may only export async functions

**Symptom.** Every part edit on a saved bike answered 500:
`A "use server" file can only export async functions, found object.`
`next build` and `tsc` were both green; only the browser saw it.

**Root cause.** `app/[locale]/velo/[id]/actions.ts` exported its zod schemas
(`updateBikePartSchema`, …) next to its actions. Next turns every export of a
`"use server"` module into a callable server reference, and a schema is an
object, so the whole module fails at request time.

**Fix.** The schemas are module-private. A test that needs one imports the
action and asserts on its `ActionResult`, which is the contract anyway.

---

## 5. Two more, cheaper, in the same session

**A `<Suspense>` around the workspace double-mounted it.** With
`useSearchParams` inside `BikeWorkspace` and a `<Suspense>` boundary around it,
hydration briefly kept the server-rendered workspace in the DOM **next to** the
client one: two parts lists, two sheets, two buttons per part, for a few hundred
milliseconds — long enough for `page.locator('[data-part-row="cassette"]')` to
be a strict-mode violation. Reading `searchParams` on the server and passing
`initialPartId` / `initialPickedIds` down (which is what §3.3 asks for anyway)
removes the boundary and the duplicate.

**`event.currentTarget` inside a state updater is `null`.**
`setDraft((current) => ({ ...current, [key]: event.currentTarget.value }))`
throws `Cannot read properties of null` — the updater runs during the _next_
render, by which time React has cleared `currentTarget`. Read the value in the
handler, then call the setter. The symptom was a fit page whose inputs simply
did nothing, with the error only in the browser console.
