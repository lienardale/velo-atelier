# 013 — W4-T1: closing the W3 follow-ups, and what closing them turned up

**Date** 2026-09-21 · **Status** resolved (§2 stays open, in the backlog) · **Branch** `w4/t1`

The task's work is in its commits (coverage include, §4.7 gaps, the one W4
migration, the line identity, quotas, `?item=`, the brand tier and the
"Comment mesurer" drawings). This note keeps the four things that were not
visible from the task spec, and the `(verify)` results.

## 1. A prefill that cost `/acheter` 24 KB of first-load JS

`scripts/ci/build.sh` failed on the branch: `/[locale]/acheter` measured
240 187 B gzip against its 236 544 B pin. The cause was the `?item=` prefill:
`components/shop/item-prefill.ts` imported `readGuestBuildList` statically, and
`lib/checkup/storage.ts` brings `zod/mini` (a 21 845 B chunk that otherwise only
`/liste` and `/controle` load) and the checkup's reducer, reconcile and tool
data (12 398 B) with it — paid by every visit, for a panel only a build-list
link opens.

The reader stays the same function (§1.2 wants storage zod-guarded on read), but
it is now a dynamic `import()` inside the effect, run only when a guest `?item=`
is present; the panel is `aria-busy` until the read answers, and every "nothing
was pre-filled" test waits for that. After: 215 723 B (−24 464 B). Home
(195 766 B) and the guide page (166 027 B) are byte-identical before and after.
The lesson is the one `.debug/007` taught about the drawings: on a client route,
"reuse the existing reader" is a bundle decision, and only the budget sees it.

## 2. What an account can see of `doneReason` (open)

`closeRecheckedItems` writes `recheck-ok` only on lists other than the
finishing checkup's own (§5.4, by design), and `/liste` shows the bike's newest
OPEN list, which is always the list the finishing checkup has just created. So
in the natural flow an account never sees "Marqué fait par un contrôle", and an
older list's open lines drop out of view after any later checkup. The write is
proven on Postgres (`tests/integration/checkups.test.ts`), the read and the
render in e2e (`tests/e2e/build-list-refine.spec.ts`, on seeded rows); what is
missing is which list the page shows.

Every finished checkup also creates a list, even an empty one, and nothing
writes `BuildList` `DONE`/`ARCHIVED`: after ten finished checkups a bike can
finish no further one (`TOO_MANY`, the user's ruling taken literally). Neither
is changed here. Which list the page shows is a product decision, and not
creating an empty list would contradict the ruling's own example. Backlog: new.

## 3. AC3's grep and the generated client

`grep -rn "queryRawUnsafe\|executeRawUnsafe\|dangerouslySetInnerHTML" app lib components | grep -v components/mdx`
prints nothing on a fresh checkout and six lines after `prisma generate`:
Prisma 7.10.0's client declares both raw methods in
`lib/generated/prisma/internal/{class,prismaNamespace}.ts` (gitignored, like
every generated tree). Over tracked sources — `git grep` on the same pattern
and paths — it prints nothing, which is the evidence reported for AC3;
`tests/security/sql-injection.test.ts` is the gate that keeps it that way.

## 4. A vendor is a retailer or `other`

§4.2 types `chosenProduct.vendor` as `RetailerId | 'other'`, and §4.4 allows a
link off the retailers' hosts only for `other`. The guest import and the W4
readers both treated ANY vendor that is not a retailer id as `other`. The rule
now lives once, in `lib/shop/chosen-product.ts`, which `lib/guest/schema.ts`
imports, and an unknown vendor is refused on the way in and dropped on the way
out.
